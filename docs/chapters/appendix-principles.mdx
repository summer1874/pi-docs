## 1. 练习：一句输入的完整调用链

在交互模式里输入“读一下 README”并回车。下面按顺序列出它经过的每一站。每站给出源码位置和关键代码，细节回到对应章节去看。

总览：

```
editor.onSubmit → InteractiveMode 主循环 → AgentSession.prompt → Agent.prompt → runAgentLoop
→ streamAssistantResponse → streamFn → modelRuntime.streamSimple → provider.streamSimple
→ lazyApi → anthropic-messages → HTTP
← AssistantMessageEvent ← AgentEvent ← AgentSessionEvent
→ 扩展处理 → InteractiveMode 渲染 → message_end 时写入 JSONL
```

				this._state.streamingMessage = event.message;

## 2. 六条设计原则

### 原则 1：事件逐层包装

**是什么**：三层事件，下层事件被原样包在上层事件里。UI、RPC、扩展都只是订阅者。

**证据**：`AgentEvent` 的 `message_update` 直接携带 pi-ai 的 `AssistantMessageEvent`：

```ts title="packages/agent/src/types.ts:524-527"
	| { type: "message_start"; message: AgentMessage }
	// Only emitted for assistant messages during streaming
	| { type: "message_update"; message: AgentMessage; assistantMessageEvent: AssistantMessageEvent }
	| { type: "message_end"; message: AgentMessage }
```

`AgentSessionEvent` 又把 `AgentEvent` 整体并进来，再加上会话层自己的事件：

```ts title="packages/coding-agent/src/core/agent-session.ts:196-210"
export type AgentSessionEvent =
	| WithParentToolCallId<Exclude<AgentEvent, { type: "agent_end" }>>
	| {
			type: "agent_end";
			messages: AgentMessage[];
			willRetry: boolean;
	  }
	| { type: "agent_settled"; aborted: boolean }
	| {
			type: "queue_update";
			steering: readonly string[];
			followUp: readonly string[];
	  }
	| { type: "compaction_start"; reason: "manual" | "threshold" | "overflow" }
	| { type: "entry_appended"; entry: SessionEntry }
```

**好处**：每层只加自己知道的信息，不丢下层细节。交互模式、print 模式、RPC 模式订阅同一个 `AgentSession`，所以行为一致。相关章节：[第 1 章](/chapters/ch01-pi-ai)、[第 2 章](/chapters/ch02-agent-core)、[第 7 章](/chapters/ch07-ui)。

### 原则 2：消息只在边界转换

**是什么**：agent 内部一直用信息更丰富的 `AgentMessage`，只在调用模型前一刻转成 pi-ai 的 `Message[]`。

**证据**：转换只发生在 `streamAssistantResponse` 一处（见上文第 4 站，[agent-loop.ts:397-404](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/agent/src/agent-loop.ts#L397-L404)）。coding-agent 的 `convertToLlm` 定义了自定义消息怎么变成模型能理解的消息：

```ts title="packages/coding-agent/src/core/messages.ts:148-175"
export function convertToLlm(messages: AgentMessage[]): Message[] {
	return messages
		.map((m): Message | undefined => {
			switch (m.role) {
				case "bashExecution":
					// Skip messages excluded from context (!! prefix)
					if (m.excludeFromContext) {
						return undefined;
					}
					return {
						role: "user",
						content: [{ type: "text", text: bashExecutionToText(m) }],
						timestamp: m.timestamp,
					};
				case "custom": {
					const content = typeof m.content === "string" ? [{ type: "text" as const, text: m.content }] : m.content;
					return {
						role: "user",
						content,
						timestamp: m.timestamp,
					};
				}
				case "branchSummary":
					return {
						role: "user",
						content: [{ type: "text" as const, text: BRANCH_SUMMARY_PREFIX + m.summary + BRANCH_SUMMARY_SUFFIX }],
						timestamp: m.timestamp,
					};
```

**好处**：`bashExecution`、`branchSummary` 这些消息在会话和 UI 里保留完整结构（命令、退出码、摘要来源），模型只看到它需要的文本。用 `!!` 执行的命令带 `excludeFromContext`，在边界处直接丢弃。相关章节：[第 2 章](/chapters/ch02-agent-core)、[第 3 章](/chapters/ch03-coding-agent)。

### 原则 3：会话是只追加的树

**是什么**：每条 entry 用 `id/parentId` 挂在树上，文件只追加不改写。当前上下文是从叶子沿父指针走回根得到的一条路径。

**证据**：`appendMessage` 总是以当前叶子为父（见上文第 11 站）；持久化用 `appendFileSync`。读取活动分支：

```ts title="packages/coding-agent/src/core/session-manager.ts:1479-1489"
	getBranch(fromId?: string): SessionEntry[] {
		const path: SessionEntry[] = [];
		const startId = fromId ?? this.leafId;
		let current = startId ? this.byId.get(startId) : undefined;
		while (current) {
			path.push(current);
			current = current.parentId ? this.byId.get(current.parentId) : undefined;
		}
		path.reverse();
		return path;
	}
```

**好处**：从旧节点继续对话只是把 `leafId` 移回去再追加，旧分支原样留在文件里；compaction 追加一条摘要 entry，不删除旧消息。崩溃时最多丢最后一行。codemode 的 `store()` 写入也是作为自定义 entry 追加的，所以天然按分支隔离（[第 8 章](/chapters/ch08-small-packages)）。相关章节：[第 5 章](/chapters/ch05-session)。

### 原则 4：Provider 和 API 解耦，按需加载

**是什么**：provider 负责鉴权和模型列表，API 负责传输协议。多个 provider 共用一个 API 实现，API 实现在第一次请求时才加载。

**证据**：groq、cerebras、deepseek 三个 provider 的 `api` 都是同一个 `openAICompletionsApi()`（[groq.ts:13](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/ai/src/providers/groq.ts#L13)、[cerebras.ts:13](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/ai/src/providers/cerebras.ts#L13)、[deepseek.ts:13](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/ai/src/providers/deepseek.ts#L13)）。懒加载由 `lazyApi` 实现：

```ts title="packages/ai/src/api/lazy.ts:98-104"
export function lazyApi(load: () => Promise<ProviderStreams>, capabilities?: LazyApiCapabilities): ProviderStreams {
	const api: ProviderStreams = {
		stream: (model, context, options) =>
			lazyStream(model, async () => (await load()).stream(model, context, options)),
		streamSimple: (model, context, options) =>
			lazyStream(model, async () => (await load()).streamSimple(model, context, options)),
	};
```

**好处**：加一个 OpenAI 兼容的 provider 只需要写鉴权和模型列表；启动时不加载 15 种协议的实现。第 10 章的入口预算检查（`check-entry-graphs.mjs`）保证这种懒加载不会被无意中破坏。相关章节：[第 1 章](/chapters/ch01-pi-ai)、[第 10 章](/chapters/ch10-engineering)。

### 原则 5：钩子分三层

**是什么**：agent-core 定义钩子接口但不实现；AgentSession 实现这些钩子；实现的内容是把调用转发成扩展事件。

**证据**：以工具调用前的拦截为例。第一层，agent-core 只声明一个可选回调：

```ts title="packages/agent/src/types.ts:319-326"
	/**
	 * Called before a tool is executed, after arguments have been validated.
	 *
	 * Return `{ block: true }` to prevent execution. The loop emits an error tool result instead.
	 * A blocked result can also set `terminate: true` to participate in the batch early-termination rule.
	 * The hook receives the agent abort signal and is responsible for honoring it.
	 */
	beforeToolCall?: (context: BeforeToolCallContext, signal?: AbortSignal) => Promise<BeforeToolCallResult | undefined>;
```

第二层，AgentSession 装上实现；第三层，实现内容是发出扩展的 `tool_call` 事件：

```ts title="packages/coding-agent/src/core/agent-session.ts:652-674"
	private _installAgentToolHooks(): void {
		this.agent.beforeToolCall = (context) => this._beforeToolCall(context);
		this.agent.afterToolCall = (context) => this._afterToolCall(context);
	}

	/** `tool_call` handlers. `parentToolCallId` is set for calls another tool made. */
	private async _beforeToolCall(
		{ toolCall, args }: BeforeToolCallContext,
		parentToolCallId?: string,
	): Promise<BeforeToolCallResult | undefined> {
		const runner = this._extensionRunner;
		if (!runner.hasHandlers("tool_call")) {
			return undefined;
		}

		try {
			return await runner.emitToolCall({
				type: "tool_call",
				toolName: toolCall.name,
				toolCallId: toolCall.id,
				...(parentToolCallId ? { parentToolCallId } : {}),
				input: args as Record<string, unknown>,
			});
```

`transformContext` 是同样的结构：agent-core 在第 4 站调用它，`sdk.ts` 把它实现为 `runner.emitContext(messages)`（[sdk.ts:428-432](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/sdk.ts#L428-L432)）。

**好处**：agent-core 不知道扩展的存在，保持 2.5k 行，可以单独使用；扩展作者面对的是稳定的事件名，而不是 agent-core 的内部接口。相关章节：[第 2 章](/chapters/ch02-agent-core)、[第 3 章](/chapters/ch03-coding-agent)、[第 6 章](/chapters/ch06-extensions)。

### 原则 6：小核心 + 扩展

**是什么**：核心不内置 sub-agent、plan mode 和权限系统。这些交给扩展；真正需要隔离时靠容器或沙箱。

**证据**：CONTRIBUTING.md 开篇就是这一条：

```md title="CONTRIBUTING.md:7-11"
First things first: **pi's core is minimal**.

If your feature does not belong in the core, it should be an extension. PRs that bloat the core will likely be rejected.

Pi's core exists to be minimal and to be extensible so that it can be influenced and manipulated by extensions.  Even hook points for extensions however should be well considered and discussed to avoid adding unmaintainable bloat and complex interactions.
```

文档也直说工具用的是 pi 进程自己的系统权限：

```md title="packages/coding-agent/docs/how-pi-works.md:47-49"
## Trust and permissions

Pi resolves project trust before loading project settings and resources. After the trust decision and project-resource loading, Pi loads context files. Enabled tools use the operating-system permissions of the Pi process. Extensions execute inside that process.
```

需要权限确认时，写一个扩展订阅 `tool_call` 即可，示例只有 30 多行：

```ts title="packages/coding-agent/examples/extensions/permission-gate.ts:10-34"
export default function (pi: ExtensionAPI) {
	const dangerousPatterns = [/\brm\s+(-rf?|--recursive)/i, /\bsudo\b/i, /\b(chmod|chown)\b.*777/i];

	pi.on("tool_call", async (event, ctx) => {
		if (event.toolName !== "bash") return undefined;

		const command = event.input.command as string;
		const isDangerous = dangerousPatterns.some((p) => p.test(command));

		if (isDangerous) {
			if (!ctx.hasUI) {
				// In non-interactive mode, block by default
				return { block: true, reason: "Dangerous command blocked (no UI for confirmation)" };
			}

			const choice = await ctx.ui.select(`⚠️ Dangerous command:\n\n  ${command}\n\nAllow?`, ["Yes", "No"]);

			if (choice !== "Yes") {
				return { block: true, reason: "Blocked by user" };
			}
		}

		return undefined;
	});
}
```

`examples/extensions/` 下还有 `plan-mode`、`subagent`、`sandbox`、`gondolin` 等目录，分别实现计划模式、子 agent 和沙箱隔离。连 MCP 和 codemode 也是以内置扩展的形式放在 `src/extensions/` 下，而不是写进 AgentSession（[第 8 章](/chapters/ch08-small-packages)）。

**好处**：核心小，读得完、改得动；不同用户要的权限模型差别很大，交给扩展比在核心里做一个“折中方案”更合适。相关章节：[第 6 章](/chapters/ch06-extensions)、[第 8 章](/chapters/ch08-small-packages)。

## 小结

| 原则 | 一句话 | 关键源码 |
|---|---|---|
| 事件逐层包装 | 下层事件原样包进上层事件 | `agent/src/types.ts:524-527`、`agent-session.ts:196-210` |
| 消息只在边界转换 | 调用模型前才 `convertToLlm` | `agent-loop.ts:397-404`、`messages.ts:148` |
| 会话是只追加的树 | `parentId` 连成树，`appendFileSync` 追加 | `session-manager.ts:1214-1224`、`1479-1489` |
| Provider 与 API 解耦 | provider 管鉴权，API 管协议，按需 import | `api/lazy.ts:98-104`、`api/anthropic-messages.lazy.ts:4` |
| 钩子分三层 | core 声明、session 实现、扩展订阅 | `agent/src/types.ts:326`、`agent-session.ts:652-674` |
| 小核心 + 扩展 | 权限、计划、子 agent 都是扩展 | `CONTRIBUTING.md:7-11`、`examples/extensions/permission-gate.ts` |
