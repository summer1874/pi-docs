## 1. 仓库布局

pi 是一个 npm workspaces monorepo。根 `package.json` 声明了工作区：

```json title="package.json:1-13"
{
	"name": "pi-monorepo",
	"private": true,
	"type": "module",
	"workspaces": [
		"packages/*",
		"apps/*",
		"packages/coding-agent/examples/extensions/with-deps",
		"packages/coding-agent/examples/extensions/custom-provider-anthropic",
		"packages/coding-agent/examples/extensions/custom-provider-gitlab-duo",
		"packages/coding-agent/examples/extensions/sandbox",
		"packages/coding-agent/examples/extensions/gondolin"
	],
```

除了 `packages/*`，几个带自己依赖的示例扩展也是工作区，这样它们的依赖会被一起安装，`tsc` 能检查它们。

`packages/` 下有 11 个目录：agent、ai、chord、codemode、coding-agent、durable、env、evals、mcp、telemetry、tui。其中 `evals` 是私有包（`"private": true`），不发布。

## 2. 构建顺序

### 2.1 build 脚本是一条串行链

```json title="package.json:16"
		"build": "cd packages/telemetry && npm run build && cd ../chord && npm run build && cd ../tui && npm run build && cd ../codemode && npm run build && cd ../mcp && npm run build && cd ../ai && npm run build && cd ../durable && npm run build && cd ../env && npm run build && cd ../agent && npm run build && cd ../coding-agent && npm run build",
```

顺序是：telemetry → chord → tui → codemode → mcp → ai → durable → env → agent → coding-agent。

为什么是这个顺序？把每个包 `dependencies` 里的内部包列出来（从各包 `package.json` 读出）：

| 包 | 依赖的内部包 |
|---|---|
| telemetry | 无 |
| chord | pi-telemetry |
| tui | 无 |
| codemode | 无 |
| mcp | 无 |
| ai | pi-telemetry |
| durable | chord、pi-ai、pi-codemode、pi-telemetry |
| env | chord、pi-durable |
| agent | pi-ai |
| coding-agent | pi-agent-core、pi-ai、pi-codemode、pi-mcp、pi-tui |

build 顺序就是这张表的一个拓扑排序：每个包都排在它依赖的所有包之后。

### 2.2 为什么必须按顺序

每个包的 `build` 是 `tsc -p tsconfig.build.json`。关键在于构建配置里的 `paths` 指向的是**下层包的 dist**，而不是源码：

```json title="packages/coding-agent/tsconfig.build.json:1-16"
{
	"extends": "../../tsconfig.base.json",
	"compilerOptions": {
		"outDir": "./dist",
		"paths": {
			"@earendil-works/pi-agent-core": ["../agent/dist/index.d.ts"],
			"@earendil-works/pi-agent-core/*": ["../agent/dist/*.d.ts"],
			"@earendil-works/pi-ai": ["../ai/dist/index.d.ts"],
			"@earendil-works/pi-ai/*": ["../ai/dist/*.d.ts", "../ai/dist/providers/*.d.ts"],
			"@earendil-works/pi-tui": ["../tui/dist/index.d.ts"],
			"@earendil-works/pi-tui/*": ["../tui/dist/*.d.ts", "../tui/dist/components/*.d.ts"]
		},
		"rootDir": "./src"
	},
	"include": ["src/**/*.ts", "src/**/*.d.ts"],
	"exclude": ["node_modules", "dist", "src/experimental"]
}
```

coding-agent 编译时要读 `../agent/dist/index.d.ts`。如果 agent 还没构建，这个文件不存在，编译失败。这样做是为了让每个包的产物和它发布到 npm 后被使用的方式一致：发布出去的 coding-agent 依赖的就是 pi-agent-core 的 `dist`。

coding-agent 的 build 比别的包多两步：

```json title="packages/coding-agent/package.json:33-34"
		"build": "npm run build:unbundled && node ../../scripts/build-coding-agent-bundle.mjs",
		"build:unbundled": "tsc -p tsconfig.build.json && shx chmod +x dist/cli.js dist/rpc-entry.js && npm run copy-assets",
```

先 `tsc` 出非打包产物并复制主题、图片等资源，再用 esbuild 打一个 `dist/bundle/cli.js`。`package.json` 里的 `bin.pi` 指向的就是这个 bundle。

### 2.3 什么时候需要 build

AGENTS.md 对 build 的用途写得很明确：只在确实需要 `dist/` 时才跑，不要拿它做类型检查：

```md title="AGENTS.md:32-33"
- After code changes (not docs): `npm run check` (full output, no tail). Fix all errors, warnings, and infos before committing. Does not run tests.
- Run `npm run build` whenever something needs built output (`dist/`): tests or benchmarks that import built packages, Durable's workerd suite. Never use it to type check or lint: that is `npm run check`, the preferred check.
```

日常开发几乎不需要 build：第 4 节会讲，源码可以直接运行，测试也直接引用源码。

## 3. npm run check：一条检查流水线

### 3.1 全貌

```json title="package.json:21-28"
		"check": "node scripts/biome-check.mjs --write && npm run check:pinned-deps && npm run check:runtime-deps && npm run check:ts-imports && npm run check:entry-graphs && npm run check:install-lock:coding-agent && tsc --noEmit && npm run check:browser-smoke",
		"check:browser-smoke": "node scripts/check-browser-smoke.mjs",
		"check:pinned-deps": "node scripts/check-pinned-deps.mjs",
		"check:runtime-deps": "node scripts/check-runtime-deps.mjs",
		"check:package-install": "node scripts/check-package-install.mjs",
		"check:install-lock:coding-agent": "node scripts/generate-coding-agent-install-lock.mjs --check",
		"check:ts-imports": "node scripts/check-ts-relative-imports.mjs",
		"check:entry-graphs": "node scripts/check-entry-graphs.mjs",
```

用 `&&` 串起来，任何一步失败后面都不跑。各步作用：

| 步骤 | 脚本 | 检查什么 |
|---|---|---|
| 格式与 lint | `scripts/biome-check.mjs --write` | Biome 格式化并 lint，警告也算失败 |
| 版本锁定 | `scripts/check-pinned-deps.mjs` | 所有 registry 依赖必须写精确版本 |
| 运行时依赖 | `scripts/check-runtime-deps.mjs` | 源码 import 的包必须在本包 `package.json` 里声明 |
| 导入后缀 | `scripts/check-ts-relative-imports.mjs` | `.ts` 文件里不许出现相对的 `.js` 导入 |
| 入口预算 | `scripts/check-entry-graphs.mjs` | 每个公开入口能拉进多少模块有上限 |
| 安装锁 | `generate-coding-agent-install-lock.mjs --check` | coding-agent 的安装锁文件是最新的 |
| 类型检查 | `tsc --noEmit` | 整个仓库一次性类型检查 |
| 浏览器冒烟 | `scripts/check-browser-smoke.mjs` | 浏览器可用的入口能被打包 |

下面挑重要的几步看源码。

`biome-check.mjs` 是对 Biome CLI 的包装，主要是为了一个边角情况：Android（Termux）上没有 Biome 原生二进制，脚本退回到 Biome 的 WASM 绑定，一个文件一个文件地检查。正常平台上它就是带 `--error-on-warnings` 调原生 CLI：

```js title="scripts/biome-check.mjs:11-22"
const write = process.argv.includes("--write");

// Same platform table as @biomejs/biome/bin/biome.
const hasNativeBinary = ["win32", "darwin", "linux"].includes(process.platform) && ["x64", "arm64"].includes(process.arch);

if (hasNativeBinary) {
	const biomeBin = createRequire(import.meta.url).resolve("@biomejs/biome/bin/biome");
	const args = ["check", "--error-on-warnings", ...(write ? ["--write"] : []), "."];
	const result = spawnSync(process.execPath, [biomeBin, ...args], { stdio: "inherit" });
	if (result.error) throw result.error;
	process.exit(result.status ?? 1);
}
```

注意 `--write`：check 会自动改写格式，所以跑完 check 后工作区可能出现格式化带来的修改。

### 3.3 依赖版本锁定

pi 要求所有直接依赖都写死精确版本，不许用 `^1.2.3` 或 `~1.2.3`。`check-pinned-deps.mjs` 遍历仓库里所有 `package.json`：

```js title="scripts/check-pinned-deps.mjs:36-59"
const failures = [];

collectPackageJsonFiles(".");

for (const file of packageJsonFiles.sort()) {
	const packageJson = JSON.parse(readFileSync(file, "utf8"));

	for (const section of dependencySections) {
		const dependencies = packageJson[section];
		if (!dependencies) continue;

		for (const [name, specifier] of Object.entries(dependencies)) {
			if (isNonRegistrySpecifier(specifier)) continue;
			if (exactVersionPattern.test(getVersionSpecifier(specifier))) continue;
			failures.push(`${file}: ${section}.${name} must be pinned, found ${specifier}`);
		}
	}
}

if (failures.length > 0) {
	console.error("Direct registry dependencies must use exact versions:");
	for (const failure of failures) console.error(`  ${failure}`);
	process.exit(1);
}
```

`exactVersionPattern`（[check-pinned-deps.mjs:5](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/scripts/check-pinned-deps.mjs#L5)）只接受 `主.次.补丁` 加可选的预发布和构建后缀。`dependencies`、`devDependencies`、`optionalDependencies` 都检查；`workspace:`、`file:`、git 地址这类非 registry 来源跳过。内部包之间也写精确版本，例如 coding-agent 依赖 `"@earendil-works/pi-agent-core": "1.4.0"`。

为什么要这么严？范围版本意味着“同一份 `package.json` 在不同时间安装会得到不同代码”。一个间接被拉进来的新版本可能带来行为变化，甚至供应链攻击。锁死版本后，依赖的每一次变化都要在 diff 里出现，可以被审查。AGENTS.md 把这一点写成规则：

```md title="AGENTS.md:46"
- Treat npm dep and lockfile changes as reviewed code. Direct registry deps, including internal workspace deps, stay pinned to exact versions.
```

同一节还规定：安装时用 `npm install --ignore-scripts`，不运行依赖的生命周期脚本（[AGENTS.md:48](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/AGENTS.md?plain=1#L48)）；新增带生命周期脚本的依赖需要在安装锁生成脚本里显式加白名单（[AGENTS.md:50](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/AGENTS.md?plain=1#L50)）。

### 3.4 运行时依赖声明

`check-runtime-deps.mjs` 用 TypeScript 的 AST 扫描每个公开包的源码，确认 import 的每个包都在本包的 `dependencies`、`optionalDependencies` 或 `peerDependencies` 里：

```js title="scripts/check-runtime-deps.mjs:26-33"
function checkSource(source, manifest) {
	const file = source.fileName;
	const declared = new Set([
		manifest.name,
		...Object.keys(manifest.dependencies ?? {}),
		...Object.keys(manifest.optionalDependencies ?? {}),
		...Object.keys(manifest.peerDependencies ?? {}),
	]);
```

在 monorepo 里这个错误很容易犯：根目录 `node_modules` 里装了某个包，子包没声明也能 import 成功，本地一切正常，发布后用户一装就报“找不到模块”。这个检查在提交前就把它拦下来。

### 3.5 入口预算

`check-entry-graphs.mjs` 的文件头把问题讲得很清楚：

```js title="scripts/check-entry-graphs.mjs:2-12"
/**
 * Entry points are cost contracts.
 *
 * A package's `exports` map is the only place that says which modules are public, and one stray
 * `export *` can silently make a narrow entry drag an entire barrel: importing a 1-file pure
 * function through a barrel costs ~37 MB of evaluated module graph, and nothing fails until someone
 * measures a process. This walks the value-import graph of every declared entry point and enforces a
 * budget per entry, so that regression fails at commit time instead.
 *
 * Only value imports count. `import type` / `export type` are erased before Node sees them.
 */
```

举例：pi-ai 的 `./models` 入口应该只拉进模型注册表和少量工具文件。如果有人在其中某个文件里加了一行 `export * from "./index.ts"`，导入 `./models` 就会把 42 个 provider 全部加载进来，启动变慢、内存上涨，但不会有任何测试失败。这个脚本为每个入口列出允许到达的模块，超出就报错。

这和第 1 章讲的 `*.lazy.ts` 懒加载是一回事的两面：懒加载让 provider 按需加载，入口预算保证懒加载不会被无意中破坏。

## 4. 只用可擦除的 TypeScript 语法

### 4.1 问题：想直接运行源码

开发时最快的循环是“改完 `.ts` 立刻运行”，不要等编译。Node 从 22.x 开始内置 TypeScript 类型剥离（strip-only 模式）：读 `.ts` 文件时，把类型注解替换成空白，剩下的就是合法 JavaScript，直接执行。

“替换成空白”这个做法有一个前提：**删掉类型之后，剩下的代码必须就是要运行的代码**。大部分 TypeScript 语法满足这个前提，比如：

```ts
// 示意（不是 pi 源码）：删掉类型注解后仍是合法 JS
function add(a: number, b: number): number { return a + b; }
type Id = string | number;
interface Point { x: number; y: number }
```

但有几种语法不满足。它们不只是类型，还会生成运行时代码，单纯删除会改变程序含义。这些语法叫“不可擦除”语法：

| 语法 | 例子（示意） | 为什么不可擦除 |
|---|---|---|
| `enum` | `enum Color { Red, Green }` | 编译成一个运行时对象 `Color` |
| 参数属性 | `constructor(private readonly x: number) {}` | 隐式生成 `this.x = x` 赋值 |
| 带值的 `namespace`/`module` | `namespace Util { export const a = 1 }` | 编译成一个 IIFE 对象 |
| `import =` | `import fs = require("fs")` | 编译成 `require` 调用 |
| `export =` | `export = foo` | 编译成 `module.exports = foo` |

以参数属性为例：

```ts
// 示意：不可擦除
class Point {
	constructor(private readonly x: number) {}
}
// 删掉类型后变成 constructor(x) {}，赋值 this.x = x 丢了
```

### 4.2 规则与编译器开关

AGENTS.md 把这条写成了硬规则：

```md title="AGENTS.md:24"
- Use only erasable TypeScript syntax (Node strip-only mode) in code checked by the root config (`packages/*/src`, `packages/*/test`, `packages/coding-agent/examples`): no parameter properties, `enum`, `namespace`/`module`, `import =`, `export =`, or other constructs needing JS emit. Use explicit fields with constructor assignments.
```

规则不只靠人记，基础配置里打开了对应的编译器选项：

```json title="tsconfig.base.json:1-23"
{
	"compilerOptions": {
		"target": "ES2024",
		"module": "Node16",
		"lib": ["ES2024"],
		"strict": true,
		"erasableSyntaxOnly": true,
		"verbatimModuleSyntax": true,
		"esModuleInterop": true,
		"skipLibCheck": true,
		"forceConsistentCasingInFileNames": true,
		"declaration": true,
		"declarationMap": true,
		"sourceMap": true,
		"inlineSources": true,
		"inlineSourceMap": false,
		"moduleResolution": "Node16",
		"resolveJsonModule": true,
		"allowImportingTsExtensions": true,
		"rewriteRelativeImportExtensions": true,
		"types": ["node"]
	}
}
```

和直接运行源码有关的四个选项：

| 选项 | 作用 |
|---|---|
| `erasableSyntaxOnly` | 用到上表任何一种语法，`tsc` 直接报错 |
| `verbatimModuleSyntax` | 只用作类型的导入必须写 `import type`。剥离器不做类型分析，分不清一个 import 是值还是类型；写明 `import type` 后整行可以安全删除 |
| `allowImportingTsExtensions` | 允许源码写 `import ... from "./foo.ts"`。Node 直接跑源码时，磁盘上只有 `foo.ts`，没有 `foo.js` |
| `rewriteRelativeImportExtensions` | `tsc` 构建 dist 时把 `./foo.ts` 改写成 `./foo.js`，发布产物照常工作 |

```ts title="packages/coding-agent/src/experimental/source-resolver.ts:6-8"
// Node strips TypeScript natively, but it does not apply the workspace source
// aliases from tsconfig.json. Internal source processes preload this resolver so
// they cannot silently fall through to stale package dist files.
```

```ts title="packages/coding-agent/src/experimental/source-resolver.ts:45-62"
registerHooks({
	resolve(specifier, context, nextResolve) {
		let matchedPattern: string | undefined;
		for (const alias of aliases) {
			const wildcard = matchAlias(alias, specifier);
			if (wildcard === undefined) continue;
			matchedPattern ??= alias.pattern;
			for (const replacement of alias.replacements) {
				const resolved = resolveSourcePath(replacement.replace("*", wildcard));
				if (resolved) return { url: pathToFileURL(resolved).href, shortCircuit: true };
			}
		}
		if (matchedPattern) {
			throw new Error(`Source runtime could not resolve ${specifier} through tsconfig path ${matchedPattern}`);
		}
		return nextResolve(specifier, context);
	},
});
```

注意找不到时是抛错而不是回退到 `nextResolve`：宁可失败，也不要静悄悄地用上旧的 dist。

### 5.2 faux provider：预先排好的模型回复

会话写成真实的 JSONL 文件，评测结束后可以回看模型每一步做了什么。

### 6.3 文档增益评测

`*.docs.eval.ts` 回答的问题是“文档有没有用”。README 描述了两个变体：`without_docs` 去掉 coding-agent 的 `README.md`、`CHANGELOG.md`、`docs/`、`examples/`，并从默认系统提示里删掉指向文档的段落；`with_docs` 保留它们。两个变体安装同一份本地打包的工作区包。每次运行用全新容器、全新 home 目录，评测定义文件在 harness 降权后对 agent 不可读，防止模型“偷看答案”。

运行器先列出完整的 `(用例, 变体, 模型, 第几次)` 计划，再逐个执行，最后成对比较。任何一对里有缺失、重复或出错的结果，就不给出总的通过率差值（[packages/evals/README.md](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/evals/README.md?plain=1)）。这是在用统计上的谨慎对付模型输出的随机性。

一个文档评测的例子：让模型给正在运行的 pi 加一个模型配置，再用结构化判定器严格比较结果：

```ts title="packages/evals/evals/models.docs.eval.ts:25-40"
const harness = createPiDocumentationEvalHarness({
	output: ({ session }) => inspectAddedModel(session.modelRuntime, PROVIDER_ID, MODEL_ID),
});
const judge = StructuredOutputJudge({ expected, match: "strict", allowExtras: false });

describeEval("Add model to existing provider", { harness, judges: [judge], judgeThreshold: null }, (it) => {
	it("adds the model without replacing existing models", async ({ run }) => {
		await run([
			{
				type: "prompt",
				content: `Configure this running Pi installation with a new \`${PROVIDER_ID}/${MODEL_ID}\` model. Do not create project-local configuration. Show it as “${MODEL_NAME}”. It accepts text, supports reasoning, has a 32,768-token context window and a 4,096-token maximum output, and has no usage cost.`,
			},
			{ type: "reload" },
		]);
	});
});
```

判定不看模型说了什么，而是读 `session.modelRuntime` 里实际注册的模型，这让评测结果客观可比。

## 7. AGENTS.md：给贡献者（包括 AI agent）的工程约束

pi 的 CONTRIBUTING.md 说：如果你用 agent 写代码，请从仓库根目录运行它，让它读到 `AGENTS.md`，并遵守其中的规则。所以 AGENTS.md 同时是给人和给 AI 的工程规范。按主题总结如下：

| 主题 | 规则 | 原因 |
|---|---|---|
| 类型 | 不用 `any`，除非绝对必要；外部 API 的类型去 `node_modules` 查，不猜 | Biome 关了 `noExplicitAny`，靠人守 |
| 导入 | 不用内联导入（`await import()`、`import("pkg").Type`），只用顶层 import | 依赖关系一眼可见，入口预算脚本也依赖静态 import |
| 语法 | 只用可擦除语法 | 第 4 节 |
| 资源路径 | coding-agent 里用 `src/config.ts` 的辅助函数解析资源，不直接用 `__dirname` | 源码运行、npm 安装、单文件二进制三种情况路径不同 |
| 依赖 | 精确版本；`--ignore-scripts` 安装；升级 `undici` 必须先读变更日志 | 供应链安全 |
| 快捷键 | 不硬编码按键判断，加到默认快捷键表里 | 保证可配置 |
| 生成文件 | 不手改 `models.generated.ts`，改生成脚本再重新生成 | 手改会被下次生成覆盖 |
| 命令 | 改完代码跑 `npm run check`；不跑全量 vitest；用 `./test.sh` 或单个测试文件 | 第 3、5 节 |
| 测试 | 新建或修改测试必须跑通；suite 测试只用 harness + faux | 确定、免费、可在 CI 跑 |
| 兼容 | 不保留向后兼容，除非用户要求；删除看起来有意为之的代码前先问 | 保持代码简洁，又避免误删 |
| Git | 只提交自己改的文件；显式 `git add <path>`；禁止 `reset --hard`、`stash`、`add -A`、`--no-verify` | 多个 agent 会话可能同时在同一工作区改不同文件 |
| 变更日志 | 只往 `## [Unreleased]` 下追加；已发布版本的段落不可改 | 发布记录不可变 |

其中 Git 那一条很能说明 pi 的开发方式。AGENTS.md 的解释是：

```md title="AGENTS.md:55"
Multiple pi sessions may be running in this cwd at the same time, each modifying different files. Git operations that touch unstaged, staged, or untracked files outside your own changes will stomp on other sessions' work. Follow these rules:
```

也就是说，维护者会在同一个工作目录里同时开多个 pi 会话各改一部分代码。`git stash` 或 `git add -A` 会把别的会话还没完成的修改卷进来或弄丢，所以被列为禁止操作。

还有几条是代码风格规则，也写在 AGENTS.md 的 Code Quality 一节：只有一个调用点的单行辅助函数要内联；类型错误来自过时依赖时，升级依赖，不要删代码迁就类型（[AGENTS.md:18-28](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/AGENTS.md?plain=1#L18-L28)）。

## 小结

- **构建**：根 `build` 按依赖拓扑顺序串行编译；各包的构建配置从下层包的 `dist/*.d.ts` 取类型，所以顺序不能乱。日常开发不需要 build。
- **检查**：`npm run check` 依次跑 Biome、精确版本检查、运行时依赖声明、导入后缀、入口预算、安装锁、全仓库 `tsc --noEmit`、浏览器冒烟。pre-commit 钩子强制执行。
- **可擦除语法**：`enum`、参数属性、带值的 namespace、`import =`、`export =` 会生成运行时代码，Node 的类型剥离处理不了。`erasableSyntaxOnly` 在编译期拦截；源码用 `.ts` 后缀导入，构建时改写成 `.js`。换来的是 `pi-test.sh`、pi-tui 测试、evals 运行器等直接跑源码。
- **测试**：vitest 通过别名直接引用源码；faux provider 按队列返回回复，并模拟真实的流式事件；`test/suite/harness.ts` 搭一套真实的 AgentSession，只替换模型；`./test.sh` 用 `env -i` 在空环境里跑，自动跳过 e2e。
- **评测**：`packages/evals` 用真实模型跑 `vitest-evals`，文档增益评测在成对容器里比较有无文档的通过率。
- **AGENTS.md**：类型、导入、依赖安全、命令、测试和 Git 的规则，同时约束人和 AI agent。
