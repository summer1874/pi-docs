## 1. 工具在整个系统里的位置

第 2 章讲过，agent-core 的循环只认识 `AgentTool`：一个带 `name`、`parameters`（TypeBox schema，一种用 TS 写 JSON Schema 的库）和 `execute()` 的对象。模型发出工具调用后，循环会依次做参数预处理、schema 校验、`beforeToolCall`、`execute`、`afterToolCall`。

coding-agent 在这之上又加了一层 `ToolDefinition`。原因是 coding-agent 需要比 `AgentTool` 更多的信息：

- 系统提示里要列出“可用工具”和“使用守则”，需要 `promptSnippet` 和 `promptGuidelines`。
- TUI 要给每个工具画专门的界面，需要 `renderCall`、`renderResult`。
- 扩展注册的工具在执行时需要拿到会话上下文（cwd、当前模型、sessionManager 等），需要第五个参数 `ctx`。

所以内置工具和扩展工具都先写成 `ToolDefinition`，交给 agent-core 之前再包装成 `AgentTool`。内置工具一共八个：

| 工具 | 文件 | 默认启用 | 只读 | 底层实现 |
| --- | --- | --- | --- | --- |
| read | `read.ts` | 是 | 是 | `fs.readFile` + 图片处理 |
| bash | `bash.ts` | 是 | 否 | `child_process.spawn` |
| edit | `edit.ts` + `edit-diff.ts` | 是 | 否 | 文本替换 + `diff` 库 |
| write | `write.ts` | 是 | 否 | `fs.writeFile` |
| grep | `grep.ts` | 否 | 是 | ripgrep（`rg --json`） |
| find | `find.ts` | 否 | 是 | fd |
| ls | `ls.ts` | 否 | 是 | `fs.readdir` + `stat` |
| powershell | `powershell.ts` | 否 | 否 | 复用 bash 的实现 |

默认只启用 read、bash、edit、write 四个。grep、find、ls 能做的事 bash 都能做，单独列出来是为了给只读场景（例如 plan 模式扩展）一个不能执行命令的工具集。

## 2. 统一形状：ToolDefinition

### 2.1 接口定义

`ToolDefinition` 定义在 [extensions/types.ts:585](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/extensions/types.ts#L585-L662)。内置工具和扩展工具用的是同一个接口，这也是 pi “小核心 + 扩展”思路的体现：内置工具没有特权。

```ts title="packages/coding-agent/src/core/extensions/types.ts:585-662"
export interface ToolDefinition<TParams extends TSchema = TSchema, TDetails = unknown, TState = any> {
	/** Tool name (used in LLM tool calls) */
	name: string;
	/** Human-readable label for UI */
	label: string;
	/** Description for LLM */
	description: string;
	/** Optional one-line snippet for the Available tools section in the default system prompt. Custom tools are omitted from that section when this is not provided. */
	promptSnippet?: string;
	/** Optional guideline bullets appended to the default system prompt Guidelines section when this tool is active. */
	promptGuidelines?: string[];
	/** Parameter schema (TypeBox) */
	parameters: TParams;
	/** Optional provider-side constrained sampling request for this tool. Set false to explicitly disable it, equivalent to leaving it undefined. */
	constrainedSampling?: false | ConstrainedSamplingConfig;
	/** Controls whether ToolExecutionComponent renders the standard colored shell or the tool renders its own framing. */
	renderShell?: "default" | "self";

	/** Optional compatibility shim to prepare raw tool call arguments before schema validation. Must return an object conforming to TParams. */
	prepareArguments?: (args: unknown) => Static<TParams>;

	/**
	 * JSON Schema of `structuredContent` in successful results. Tools that declare it should always
	 * set `structuredContent`; codemode scripts then receive it instead of the text content.
	 */
	outputSchema?: TSchema;
	// ...
	executionMode?: ToolExecutionMode;

	/** Execute the tool. */
	execute(
		toolCallId: string,
		params: Static<TParams>,
		signal: AbortSignal | undefined,
		onUpdate: AgentToolUpdateCallback<TDetails> | undefined,
		ctx: ExtensionToolContext,
	): Promise<AgentToolResult<TDetails>>;
```

几个字段的作用：

- `description` 发给模型，是模型了解工具的唯一途径。内置工具会把截断上限直接写进描述，例如 read 的描述里有“truncated to 2000 lines or 50KB”，让模型事先知道要用 `offset/limit` 分页。
- `prepareArguments` 在 schema 校验之前运行，用来兼容模型发错格式的参数。edit 工具就靠它修正几种常见错误（见第 6 节）。
- `outputSchema` 和结果里的 `structuredContent` 给程序化调用方用，例如 codemode 脚本（第 8 章）。模型看到的是 `content`，脚本拿到的是 `structuredContent`。
- `constrainedSampling` 请求 provider 按 JSON schema 约束采样，内置的 read、bash、edit、write 都设成 `{ type: "json_schema", strict: "prefer" }`。
- `executionMode` 可以把某个工具强制设为串行。内置工具都没有设置，所以它们会并行执行，这就是第 5 节文件写队列存在的原因。

### 2.2 包装成 AgentTool

[tool-definition-wrapper.ts](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/tools/tool-definition-wrapper.ts#L8-L30) 只有 58 行，做两个方向的转换。

```ts title="packages/coding-agent/src/core/tools/tool-definition-wrapper.ts:4-30"
/** Creates the context for one tool call. */
export type ToolContextFactory = (toolCallId: string, signal: AbortSignal | undefined) => ExtensionToolContext;

/** Wrap a ToolDefinition into an AgentTool for the core runtime. */
export function wrapToolDefinition<TDetails = unknown>(
	definition: ToolDefinition<any, TDetails>,
	ctxFactory?: ToolContextFactory,
): AgentTool<any, TDetails> {
	return {
		name: definition.name,
		label: definition.label,
		description: definition.description,
		parameters: definition.parameters,
		outputSchema: definition.outputSchema,
		constrainedSampling: definition.constrainedSampling,
		prepareArguments: definition.prepareArguments,
		executionMode: definition.executionMode,
		execute: (toolCallId, params, signal, onUpdate, ctx?: ExtensionToolContext) =>
			definition.execute(
				toolCallId,
				params,
				signal,
				onUpdate,
				ctx ?? (ctxFactory?.(toolCallId, signal) as ExtensionToolContext),
			),
	};
}
```

要点：

1. 只拷贝 agent-core 认识的字段。`promptSnippet`、渲染器这些 coding-agent 自己用的字段不往下传。
2. `ctx` 有两个来源：调用方直接传入，或者用 `ctxFactory` 现造一个。扩展工具走 [extensions/wrapper.ts:17-21](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/extensions/wrapper.ts#L17-L21)，用 `runner.createToolContext()` 作为工厂。
3. 不带工厂直接包装时（例如 SDK 用户调用 `createBashTool(cwd)` 再放进一个普通 `Agent`），`ctx` 是 `undefined`。所以每个内置工具都写成 `ctx?.cwd || cwd`，没有上下文时退回创建时传入的 cwd。

反方向的 `createToolDefinitionFromAgentTool()` 给 SDK 用户的 `AgentTool` 覆盖项补成最小的 `ToolDefinition`，让 AgentSession 内部注册表始终以 `ToolDefinition` 为准。

### 2.4 可插拔的 Operations

每个工具都把真正碰文件系统或进程的部分抽成一个 `XxxOperations` 接口，默认实现走本地。例如 read：

```ts title="packages/coding-agent/src/core/tools/read.ts:44-61"
/**
 * Pluggable operations for the read tool.
 * Override these to delegate file reading to remote systems (for example SSH).

export interface ReadOperations {
	/** Read file contents as a Buffer */
	readFile: (absolutePath: string) => Promise<Buffer>;
	/** Check if file is readable (throw if not) */
	access: (absolutePath: string) => Promise<void>;
	/** Detect image MIME type, return null or undefined for non-images */
	detectImageMimeType?: (absolutePath: string) => Promise<string | null | undefined>;

const defaultReadOperations: ReadOperations = {
	readFile: (path) => fsReadFile(path),
	access: (path) => fsAccess(path, constants.R_OK),

```

这样做的好处是：扩展想把工具搬到远端（SSH、容器）时，只换 Operations，截断、分页、错误提示这些逻辑原样复用。bash 的 `BashOperations.exec`、edit 的 `EditOperations`、grep 的 `GrepOperations` 都是同一个思路。

## 3. 截断：truncate.ts

### 3.1 为什么要截断

模型的上下文窗口有限，而且每一轮都要把整个上下文重新发一次。一次 `cat package-lock.json` 或一次失控的测试输出就能产生几 MB 文本，直接放进上下文会有三个后果：超出窗口导致请求失败；没超也会迅速触发 compaction（第 5 章）；token 费用按轮次反复计算。

所以每个会产生大量输出的工具都要截断，截断后还要告诉模型“看到的是哪一部分、怎么拿到剩下的”。

### 3.2 两个上限，谁先到算谁

```ts title="packages/coding-agent/src/core/tools/truncate.ts:1-13"
/**
 * Shared truncation utilities for tool outputs.
 *
 * Truncation is based on two independent limits - whichever is hit first wins:
 * - Line limit (default: 2000 lines)
 * - Byte limit (default: 50KB)
 *
 * Never returns partial lines (except bash tail truncation edge case).
 */

export const DEFAULT_MAX_LINES = 2000;
export const DEFAULT_MAX_BYTES = 50 * 1024; // 50KB
export const GREP_MAX_LINE_LENGTH = 500; // Max chars per grep match line
```

两个上限各防一种情况：行数防“很多短行”（日志），字节防“少数超长行”（压缩过的 JS、单行 JSON）。50KB 大约相当于一万多 token，是一次工具结果能接受的上限。

截断方向有三种，用途不同：

| 函数 | 保留哪部分 | 用在哪里 | 理由 |
| --- | --- | --- | --- |
| `truncateHead` | 开头 | read、grep、find、ls | 读文件从头看；搜索结果前面的匹配更有代表性 |
| `truncateTail` | 结尾 | bash（经 OutputAccumulator） | 命令输出的关键信息（错误、最终结果）通常在最后 |
| `truncateMiddle` | 首尾各一半 | 内置 MCP 扩展的工具输出（`extensions/mcp/tools.ts`） | 照 Codex 的做法，头尾都可能重要 |
| `truncateLine` | 单行前 500 字符 | grep 匹配行 | 一行压缩代码不该占满结果 |

### 3.3 truncateHead：只返回完整行

```ts title="packages/coding-agent/src/core/tools/truncate.ts:78-145"
export function truncateHead(content: string, options: TruncationOptions = {}): TruncationResult {
	const maxLines = options.maxLines ?? DEFAULT_MAX_LINES;
	const maxBytes = options.maxBytes ?? DEFAULT_MAX_BYTES;

	const totalBytes = Buffer.byteLength(content, "utf-8");
	const lines = splitLinesForCounting(content);
	const totalLines = lines.length;

	// Check if no truncation needed
	if (totalLines <= maxLines && totalBytes <= maxBytes) {
		// ...
	}

	// Check if first line alone exceeds byte limit
	const firstLineBytes = Buffer.byteLength(lines[0], "utf-8");
	if (firstLineBytes > maxBytes) {
		return {
			content: "",
			truncated: true,
			truncatedBy: "bytes",
			// ...
			firstLineExceedsLimit: true,
			// ...
		};
	}

	// Collect complete lines that fit
	const outputLinesArr: string[] = [];
	let outputBytesCount = 0;
	let truncatedBy: "lines" | "bytes" = "lines";

	for (let i = 0; i < lines.length && i < maxLines; i++) {
		const line = lines[i];
		const lineBytes = Buffer.byteLength(line, "utf-8") + (i > 0 ? 1 : 0); // +1 for newline

		if (outputBytesCount + lineBytes > maxBytes) {
			truncatedBy = "bytes";
			break;
		}

		outputLinesArr.push(line);
		outputBytesCount += lineBytes;
	}
```

逐行累加字节数，加上下一行会超就停。这保证输出永远是完整的行，模型不会看到半行代码。字节数用 `Buffer.byteLength` 按 UTF-8 计算，而不是 `string.length`，中文和 emoji 都按真实字节算。

极端情况是第一行本身就超过 50KB（比如一个 minified 文件）。这时 `truncateHead` 返回空内容并设 `firstLineExceedsLimit: true`，由调用方决定怎么提示。返回的 `TruncationResult` 记录了 `truncatedBy`、`totalLines`、`outputLines` 等字段，调用方据此生成提示，同时塞进 `details` 给 TUI 显示。

### 3.4 truncateTail：从后往前，必要时切半行

```ts title="packages/coding-agent/src/core/tools/truncate.ts:193-218"
	// Work backwards from the end
	const outputLinesArr: string[] = [];
	let outputBytesCount = 0;
	let truncatedBy: "lines" | "bytes" = "lines";
	let lastLinePartial = false;

	for (let i = lines.length - 1; i >= 0 && outputLinesArr.length < maxLines; i--) {
		const line = lines[i];
		const lineBytes = Buffer.byteLength(line, "utf-8") + (outputLinesArr.length > 0 ? 1 : 0); // +1 for newline

		if (outputBytesCount + lineBytes > maxBytes) {
			truncatedBy = "bytes";
			// Edge case: if we haven't added ANY lines yet and this line exceeds maxBytes,
			// take the end of the line (partial)
			if (outputLinesArr.length === 0) {
				const truncatedLine = truncateStringToBytesFromEnd(line, maxBytes);
				outputLinesArr.unshift(truncatedLine);
				outputBytesCount = Buffer.byteLength(truncatedLine, "utf-8");
				lastLinePartial = true;
			}
			break;
		}

		outputLinesArr.unshift(line);
		outputBytesCount += lineBytes;
	}
```

和 head 版的区别在边界情况：如果最后一行本身就超过 50KB（例如一个打印了巨大 JSON 的命令），head 版会返回空，而 tail 版会取这一行的末尾 50KB，并标记 `lastLinePartial`。理由是 bash 输出没有别的办法分页，返回空等于什么都没给。`truncateStringToBytesFromEnd` 会跳过 UTF-8 的续字节（`(buf[start] & 0xc0) === 0x80`），保证不从一个多字节字符中间切开。

## 4. read：分页与图片

### 4.1 参数


### 4.2 文本：先按 limit 切，再截断，最后给续读提示

```ts title="packages/coding-agent/src/core/tools/read.ts:153-204"
							} else {
								// Read text content.
								const buffer = await ops.readFile(absolutePath);
								const textContent = buffer.toString("utf-8");
								const allLines = textContent.split("\n");
								const totalFileLines = allLines.length;
								// Apply offset if specified. Convert from 1-indexed input to 0-indexed array access.
								const startLine = offset ? Math.max(0, offset - 1) : 0;
								const startLineDisplay = startLine + 1;
								// Check if offset is out of bounds.
								if (startLine >= allLines.length) {
									throw new Error(`Offset ${offset} is beyond end of file (${allLines.length} lines total)`);
								}
								let selectedContent: string;
								let userLimitedLines: number | undefined;
								// If limit is specified by the user, honor it first. Otherwise truncateHead decides.
								if (limit !== undefined) {
									const endLine = Math.min(startLine + limit, allLines.length);
									selectedContent = allLines.slice(startLine, endLine).join("\n");
									userLimitedLines = endLine - startLine;
								} else {
									selectedContent = allLines.slice(startLine).join("\n");
								}
								// Apply truncation, respecting both line and byte limits.
								const truncation = truncateHead(selectedContent);
								let outputText: string;
								if (truncation.firstLineExceedsLimit) {
									// First line alone exceeds the byte limit. Point the model at a bash fallback.
									const firstLineSize = formatSize(Buffer.byteLength(allLines[startLine], "utf-8"));
									outputText = `[Line ${startLineDisplay} is ${firstLineSize}, exceeds ${formatSize(DEFAULT_MAX_BYTES)} limit. Use bash: sed -n '${startLineDisplay}p' ${path} | head -c ${DEFAULT_MAX_BYTES}]`;
									details = { truncation };
								} else if (truncation.truncated) {
									// Truncation occurred. Build an actionable continuation notice.
									const endLineDisplay = startLineDisplay + truncation.outputLines - 1;
									const nextOffset = endLineDisplay + 1;
									outputText = truncation.content;
									if (truncation.truncatedBy === "lines") {
										outputText += `\n\n[Showing lines ${startLineDisplay}-${endLineDisplay} of ${totalFileLines}. Use offset=${nextOffset} to continue.]`;
									} else {
										outputText += `\n\n[Showing lines ${startLineDisplay}-${endLineDisplay} of ${totalFileLines} (${formatSize(DEFAULT_MAX_BYTES)} limit). Use offset=${nextOffset} to continue.]`;
									}
									details = { truncation };
								} else if (userLimitedLines !== undefined && startLine + userLimitedLines < allLines.length) {
									// User-specified limit stopped early, but the file still has more content.
									const remaining = allLines.length - (startLine + userLimitedLines);
									const nextOffset = startLine + userLimitedLines + 1;
									outputText = `${truncation.content}\n\n[${remaining} more lines in file. Use offset=${nextOffset} to continue.]`;
								} else {
									// No truncation and no remaining user-limited content.
									outputText = truncation.content;
								}
								content = [{ type: "text", text: outputText }];
							}
```

具体例子：读一个 5000 行的文件，不带参数。`truncateHead` 在第 2000 行停下，模型收到的文本末尾是：

```text
[Showing lines 1-2000 of 5000. Use offset=2001 to continue.]
```

模型下一次调用 `read({ path, offset: 2001 })` 就能接着读。提示的四个分支对应四种情况：首行超长（建议用 `sed | head -c`）、被行数或字节截断（给出下一个 offset）、被模型自己的 `limit` 截住（告诉还剩多少行）、完整读完（不加提示）。每条提示都包含下一步要用的确切参数，模型不需要自己计算。

注意 `limit` 优先于截断：模型说“读 100 行”就先切 100 行，再交给 `truncateHead` 兜底字节上限。

### 4.3 图片

### 4.4 中止的处理方式

read 把执行包在一个 `new Promise` 里，注册 `abort` 监听：一旦中止就立刻 `reject`，后台的异步读取即使完成，也因为 `aborted` 标志而不再 `resolve`（[read.ts:109-214](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/tools/read.ts#L109-L214)）。这种“立刻返回”的做法对只读工具是安全的。第 5 节会看到，写文件的工具故意不这样做。

### 4.5 path-utils：猜测用户的意思

[path-utils.ts](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/tools/path-utils.ts) 负责把模型给的路径变成绝对路径。`resolveToCwd` 处理 `~` 展开、相对路径、Unicode 空格、以及模型常带的 `@` 前缀（从 `@file` 引用里抄来的）。

read 还多做一步 `resolveReadPathAsync`，专门对付 macOS 截图文件名：

```ts title="packages/coding-agent/src/core/tools/path-utils.ts:86-118"
export async function resolveReadPathAsync(filePath: string, cwd: string): Promise<string> {
	const resolved = resolveToCwd(filePath, cwd);

	if (await pathExists(resolved)) {
		return resolved;
	}

	// Try macOS AM/PM variant (narrow no-break space before AM/PM)
	const amPmVariant = tryMacOSScreenshotPath(resolved);
	if (amPmVariant !== resolved && (await pathExists(amPmVariant))) {
		return amPmVariant;
	}

	// Try NFD variant (macOS stores filenames in NFD form)
	const nfdVariant = tryNFDVariant(resolved);
	if (nfdVariant !== resolved && (await pathExists(nfdVariant))) {
		return nfdVariant;
	}

	// Try curly quote variant (macOS uses U+2019 in screenshot names)
	const curlyVariant = tryCurlyQuoteVariant(resolved);
	if (curlyVariant !== resolved && (await pathExists(curlyVariant))) {
		return curlyVariant;
	}

	// Try combined NFD + curly quote (for French macOS screenshots like "Capture d'écran")
	const nfdCurlyVariant = tryCurlyQuoteVariant(nfdVariant);
	if (nfdCurlyVariant !== resolved && (await pathExists(nfdCurlyVariant))) {
		return nfdCurlyVariant;
	}

	return resolved;
}
```

问题来自真实场景：用户把截图拖进终端，文件名是 `Screenshot 2024-01-01 at 10.00.00 AM.png`，但 macOS 实际在 `AM` 前用的是窄不换行空格 U+202F；法语系统的 `Capture d'écran` 用的是弯引号 U+2019，而且 `é` 以 NFD（分解形式）存储。模型输入的是普通字符，直接 `access` 会找不到。这个函数按顺序尝试几种变体，找到存在的就用；都不存在就返回原路径，让后续的 `access` 报出正常的“文件不存在”。只有 read 用这个宽松解析，写入类工具用严格的 `resolveToCwd`，避免把内容写到另一个文件里。

## 5. write 与文件写队列

### 5.1 write

write 的参数只有 `path` 和 `content`，逻辑也最简单：建父目录，写文件。

```ts title="packages/coding-agent/src/core/tools/write.ts:65-89"

			const dir = dirname(absolutePath);

				// Do not reject from an abort event listener here: that would release the

				// Checking signal.aborted after each await observes the same aborts while
				// keeping the queue locked until the current operation has settled.

					if (signal?.aborted) throw new Error("Operation aborted");
				};

				throwIfAborted();

				// Write the file contents.
				await ops.writeFile(absolutePath, content);

					content: [{ type: "text", text: `Successfully wrote to ${path}` }],
					details: undefined,
				};
			});
```

注释解释了它和 read 的中止策略为什么不同。如果像 read 那样在 `abort` 事件里立刻 `reject`，Promise 会提前结束，`withFileMutationQueue` 的 `finally` 会释放队列，可是 `writeFile` 还在后台跑。下一个排队的 edit 就可能和这次写入同时操作同一个文件。所以写入类工具只在每个 `await` 之后检查 `signal.aborted`，保证队列一直锁到文件系统操作真正结束。

返回给模型的只有一句 `Successfully wrote to ...`，不回显内容，模型自己知道写了什么。

### 5.2 为什么需要排队

agent-core 默认 `toolExecution` 是 `"parallel"`（[agent.ts:261](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/agent/src/agent.ts#L261)），内置工具都没有声明 `executionMode: "sequential"`。模型完全可能在一次回复里对同一个文件发两个 edit：

```text
edit(path="a.ts", edits=[{oldText: "foo", newText: "bar"}])
edit(path="a.ts", edits=[{oldText: "baz", newText: "qux"}])
```

两个调用并行执行时，经典的“读-改-写”竞争就出现了：两者都读到原始内容，各自替换后写回，后写的覆盖先写的，第一处修改丢失，而两个调用都报告成功。

最简单的修法是把所有工具改成串行，但那样 read、grep 这些无害的调用也被拖慢。pi 的选择是只对“写同一个文件”的操作排队，不同文件之间仍然并行。

### 5.3 withFileMutationQueue

```ts title="packages/coding-agent/src/core/tools/file-mutation-queue.ts:4-61"
const fileMutationQueues = new Map<string, Promise<void>>();
let registrationQueue = Promise.resolve();

// ...

async function getMutationQueueKey(filePath: string): Promise<string> {
	const resolvedPath = resolve(filePath);
	try {
		return await realpath(resolvedPath);
	} catch (error) {
		if (isMissingPathError(error)) {
			return resolvedPath;
		}
		throw error;
	}
}

/**
 * Serialize file mutation operations targeting the same file.
 * Operations for different files still run in parallel.
 */
export async function withFileMutationQueue<T>(filePath: string, fn: () => Promise<T>): Promise<T> {
	const registration = registrationQueue.then(async () => {
		const key = await getMutationQueueKey(filePath);
		const currentQueue = fileMutationQueues.get(key) ?? Promise.resolve();

		let releaseNext!: () => void;
		const nextQueue = new Promise<void>((resolveQueue) => {
			releaseNext = resolveQueue;
		});
		const chainedQueue = currentQueue.then(() => nextQueue);
		fileMutationQueues.set(key, chainedQueue);

		return { key, currentQueue, chainedQueue, releaseNext };
	});
	registrationQueue = registration.then(
		() => undefined,
		() => undefined,
	);

	const { key, currentQueue, chainedQueue, releaseNext } = await registration;
	await currentQueue;
	try {
		return await fn();
	} finally {
		releaseNext();
		if (fileMutationQueues.get(key) === chainedQueue) {
			fileMutationQueues.delete(key);
		}
	}
}
```

这是用 Promise 链实现的按 key 互斥锁。逐步拆开：

1. **key 用 `realpath`**。`./a.ts`、`/abs/a.ts`、指向它的符号链接，解析后是同一个 key。文件还不存在时（write 新建文件）`realpath` 报 `ENOENT`，退回到 `resolve` 后的路径。
2. **每次调用在链尾挂一个新的“门”** `nextQueue`，它只有在本次 `fn` 结束、调用 `releaseNext()` 后才 resolve。`chainedQueue = currentQueue.then(() => nextQueue)` 成为新的链尾，下一个调用者要等它。
3. **本次调用等 `currentQueue`**，也就是等前面所有人都放行，然后执行 `fn`。
4. **`finally` 里放行并清理**。如果自己仍然是链尾（后面没人排队），就从 Map 里删掉这个 key，防止 Map 无限增长。

为什么还要一个全局的 `registrationQueue`？因为 `getMutationQueueKey` 是异步的（`realpath` 要走一次文件系统）。假设 A、B 两个调用几乎同时进来，如果不串行注册，可能 A 的 `realpath` 还没返回，B 已经读了 `fileMutationQueues.get(key)` 拿到空值，两者都以为自己是第一个。`registrationQueue` 让“算 key + 读链尾 + 写链尾”这三步对所有调用串行执行。它只串行注册这一小步，`fn` 本身仍然并发，所以不同文件不会互相阻塞。`registration.then(() => undefined, () => undefined)` 吞掉错误，避免一次 `realpath` 失败卡死后面所有注册。

`withFileMutationQueue` 还从包入口导出（[sdk.ts:39](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/sdk.ts#L39)），扩展自定义的写文件工具也可以加入同一个队列。

edit 不用行号，而用“旧文本 → 新文本”的字符串替换。理由是行号很脆弱：模型看到的行号可能来自几轮之前的 read，中间文件已经被改过；文本匹配则自带校验，旧文本对不上就报错，不会悄悄改错地方。

一次调用可以带多个 `edits`，三条规则写在描述里：每个 `oldText` 在原文件中唯一；所有 edit 都对**原始**文件匹配，而不是依次在前一个 edit 的结果上匹配；不能重叠。“对原始文件匹配”让模型不用推算前面替换后文本变成了什么样。

### 6.2 prepareArguments：兼容模型的错误格式


### 6.3 执行流程

这段外面同样包着 `withFileMutationQueue`。数据流是“剥离 → 规范化 → 替换 → 还原”：

1. 剥掉 BOM（文件开头不可见的字节序标记），模型的 `oldText` 不会包含它。
2. 记下原文件的换行风格（`detectLineEnding` 看第一个换行是 `\r\n` 还是 `\n`），然后统一转成 `\n`。Windows 文件和模型输出的换行不一致是匹配失败的常见原因。
3. 在 LF 空间里做替换。
4. 写回时还原换行风格并加回 BOM，文件的格式特征保持不变。

结果分两份：给模型的 `content` 只有一句“替换了 N 处”，给 TUI 的 `details` 带完整 diff 和 unified patch。diff 对模型没用（它知道自己改了什么），放进上下文只会浪费 token。

### 6.4 匹配：先精确，再宽松

```ts title="packages/coding-agent/src/core/tools/edit-diff.ts:34-55"
export function normalizeForFuzzyMatch(text: string): string {
	return (
		text
			.normalize("NFKC")
			// Strip trailing whitespace per line
			.split("\n")
			.map((line) => line.trimEnd())
			.join("\n")
			// Smart single quotes → '
			.replace(/[\u2018\u2019\u201A\u201B]/g, "'")
			// Smart double quotes → "
			.replace(/[\u201C\u201D\u201E\u201F]/g, '"')
			// Various dashes/hyphens → -
			// U+2010 hyphen, U+2011 non-breaking hyphen, U+2012 figure dash,
			// U+2013 en-dash, U+2014 em-dash, U+2015 horizontal bar, U+2212 minus
			.replace(/[\u2010\u2011\u2012\u2013\u2014\u2015\u2212]/g, "-")
			// Special spaces → regular space
			// U+00A0 NBSP, U+2002-U+200A various spaces, U+202F narrow NBSP,
			// U+205F medium math space, U+3000 ideographic space
			.replace(/[\u00A0\u2002-\u200A\u202F\u205F\u3000]/g, " ")
	);
}
```

```ts title="packages/coding-agent/src/core/tools/edit-diff.ts:207-245"
export function fuzzyFindText(content: string, oldText: string): FuzzyMatchResult {
	// Try exact match first
	const exactIndex = content.indexOf(oldText);
	if (exactIndex !== -1) {
		return {
			found: true,
			index: exactIndex,
			matchLength: oldText.length,
			usedFuzzyMatch: false,
			contentForReplacement: content,
		};
	}

	// Try fuzzy match - work entirely in normalized space
	const fuzzyContent = normalizeForFuzzyMatch(content);
	const fuzzyOldText = normalizeForFuzzyMatch(oldText);
	const fuzzyIndex = fuzzyContent.indexOf(fuzzyOldText);

	if (fuzzyIndex === -1) {
		return {
			found: false,
			index: -1,
			matchLength: 0,
			usedFuzzyMatch: false,
			contentForReplacement: content,
		};
	}

	// When fuzzy matching, return offsets in normalized space. Callers can use
	// the normalized content to compute replacements, then decide how much of
	// that normalized output should be written back.
	return {
		found: true,
		index: fuzzyIndex,
		matchLength: fuzzyOldText.length,
		usedFuzzyMatch: true,
		contentForReplacement: fuzzyContent,
	};
}
```

宽松匹配只抹平“肉眼看不出、模型经常抄错”的差异：行尾空白、弯引号、各种破折号、特殊空格，加上 NFKC 规范化（把全角字母、合字等兼容字符折成标准形式）。它**不**忽略缩进，也不做编辑距离之类的近似匹配。缩进在 Python、YAML 里有语义，近似匹配可能改错地方，宁可报错让模型重试。

### 6.5 多处匹配、匹配失败、重叠

所有规则集中在 `applyEditsToNormalizedContent`：

```ts title="packages/coding-agent/src/core/tools/edit-diff.ts:300-362"
export function applyEditsToNormalizedContent(
	normalizedContent: string,
	edits: Edit[],
	path: string,
): AppliedEditsResult {
	const normalizedEdits = edits.map((edit) => ({
		oldText: normalizeToLF(edit.oldText),
		newText: normalizeToLF(edit.newText),
	}));

	for (let i = 0; i < normalizedEdits.length; i++) {
		if (normalizedEdits[i].oldText.length === 0) {
			throw getEmptyOldTextError(path, i, normalizedEdits.length);
		}
	}

	const initialMatches = normalizedEdits.map((edit) => fuzzyFindText(normalizedContent, edit.oldText));
	const usedFuzzyMatch = initialMatches.some((match) => match.usedFuzzyMatch);
	const replacementBaseContent = usedFuzzyMatch ? normalizeForFuzzyMatch(normalizedContent) : normalizedContent;

	const matchedEdits: MatchedEdit[] = [];
	for (let i = 0; i < normalizedEdits.length; i++) {
		const edit = normalizedEdits[i];
		const matchResult = fuzzyFindText(replacementBaseContent, edit.oldText);
		if (!matchResult.found) {
			throw getNotFoundError(path, i, normalizedEdits.length);
		}

		const occurrences = countOccurrences(replacementBaseContent, edit.oldText);
		if (occurrences > 1) {
			throw getDuplicateError(path, i, normalizedEdits.length, occurrences);
		}

		matchedEdits.push({
			editIndex: i,
			matchIndex: matchResult.index,
			matchLength: matchResult.matchLength,
			newText: edit.newText,
		});
	}

	matchedEdits.sort((a, b) => a.matchIndex - b.matchIndex);
	for (let i = 1; i < matchedEdits.length; i++) {
		const previous = matchedEdits[i - 1];
		const current = matchedEdits[i];
		if (previous.matchIndex + previous.matchLength > current.matchIndex) {
			throw new Error(
				`edits[${previous.editIndex}] and edits[${current.editIndex}] overlap in ${path}. Merge them into one edit or target disjoint regions.`,
			);
		}
	}

	const baseContent = normalizedContent;
	const newContent = usedFuzzyMatch
		? applyReplacementsPreservingUnchangedLines(normalizedContent, replacementBaseContent, matchedEdits)
		: applyReplacements(replacementBaseContent, matchedEdits);

	if (baseContent === newContent) {
		throw getNoChangeError(path, normalizedEdits.length);
	}

	return { baseContent, newContent };
}
```

按顺序列出所有失败情况和对应的错误信息：

| 情况 | 检查位置 | 给模型的错误 |
| --- | --- | --- |
| `oldText` 为空 | 第 310-314 行 | `oldText must not be empty` |
| 精确和宽松都找不到 | 第 324-326 行 | `Could not find the exact text ... must match exactly including all whitespace and newlines` |
| 找到不止一处 | 第 328-331 行 | `Found N occurrences ... Please provide more context to make it unique` |
| 两个 edit 区域重叠 | 第 341-350 行 | `edits[i] and edits[j] overlap ... Merge them into one edit` |
| 替换后内容没变 | 第 357-359 行 | `No changes made ... produced identical content` |

几个设计细节：

- **多处匹配直接报错，不猜。** 文件里有三处 `return null;`，模型说把 `return null;` 换成 `return undefined;`，工具不会替换第一处，也不会全部替换，而是告诉模型“找到 3 处，请加上下文”。模型通常会把前后一两行一起放进 `oldText` 再试。`countOccurrences` 在宽松规范化后的空间里计数，所以即使精确匹配只命中一处，只要宽松空间里有多处也算重复。
- **一个失败全部回滚。** 所有检查都在写文件之前完成，任何一个 edit 失败就抛错，文件完全不动。不会出现“三处改了两处”的中间状态。
- **一个 edit 用了宽松匹配，整批都在宽松空间里匹配。** 第 316-318 行先用原文试一遍，只要有一个需要宽松匹配，就把整个文件转成宽松形式，所有 edit 重新在这个统一的坐标系里定位。这样所有偏移量可比较，重叠检测才成立。
- **从后往前替换。** `applyReplacements` 按偏移从大到小替换（[edit-diff.ts:111-120](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/tools/edit-diff.ts#L111-L120)），后面的替换不会改变前面区域的偏移。

### 6.6 宽松匹配时保住没改的行

宽松匹配有个副作用：如果直接把规范化后的整个文件写回，没有被编辑的行里的弯引号、行尾空格也会被“顺手”改掉，产生一大片无关 diff。`applyReplacementsPreservingUnchangedLines` 解决这个问题：

```ts title="packages/coding-agent/src/core/tools/edit-diff.ts:132-173"
export function applyReplacementsPreservingUnchangedLines(
	originalContent: string,
	baseContent: string,
	replacements: TextReplacement[],
): string {
	const originalLines = splitLinesWithEndings(originalContent);
	const baseLines = getLineSpans(baseContent);
	if (originalLines.length !== baseLines.length) {
		throw new Error("Cannot preserve unchanged lines because the base content has a different line count.");
	}

	const groups: Array<{ startLine: number; endLine: number; replacements: TextReplacement[] }> = [];
	const sortedReplacements = [...replacements].sort((a, b) => a.matchIndex - b.matchIndex);
	for (const replacement of sortedReplacements) {
		const range = getReplacementLineRange(baseLines, replacement);
		const current = groups[groups.length - 1];
		if (current && range.startLine < current.endLine) {
			current.endLine = Math.max(current.endLine, range.endLine);
			current.replacements.push(replacement);
			continue;
		}
		groups.push({ ...range, replacements: [replacement] });
	}

	let originalLineIndex = 0;
	let result = "";
	for (const group of groups) {
		result += originalLines.slice(originalLineIndex, group.startLine).join("");

		const groupStartOffset = baseLines[group.startLine].start;
		const groupEndOffset = baseLines[group.endLine - 1].end;
		result += applyReplacements(
			baseContent.slice(groupStartOffset, groupEndOffset),
			group.replacements,
			groupStartOffset,
		);
		originalLineIndex = group.endLine;
	}
	result += originalLines.slice(originalLineIndex).join("");

	return result;
}
```

做法是按行拼接：被替换触及的行从规范化版本里取（这几行本来就要改），其他行原样从原文件拷贝。规范化不会增删换行，所以两个版本行数相同，可以按行号对齐。这样宽松匹配的影响被限制在真正编辑的那几行。

### 6.7 diff 生成

`generateDiffString`（[edit-diff.ts:376-499](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/tools/edit-diff.ts#L376-L499)）用 `diff` 库的 `diffLines` 算出增删块，再自己格式化成带行号的显示用 diff：增加行前缀 `+`，删除行前缀 `-`，变更前后各保留 4 行上下文，中间省略的部分用 `...` 代替。它还记下 `firstChangedLine`，编辑器集成可以据此跳到第一处修改。`generateUnifiedPatch` 则生成标准 unified patch，供导出或外部工具使用。

### 7.2 启动子进程与杀进程树

`createLocalShellOperations` 是 bash 和 powershell 共用的执行后端：

```ts title="packages/coding-agent/src/core/tools/bash.ts:99-164"

				}

				}

				// callers do not mistake the termination for a successful command.

				if (timeoutHandle) clearTimeout(timeoutHandle);
				if (signal) signal.removeEventListener("abort", onAbort);
```

关键决定：

- **`detached: true`（非 Windows）**。子 shell 成为新进程组的组长。之后杀进程时用 `process.kill(-pid)` 向整个组发信号，`npm test` 派生出的 node、浏览器等孙进程一起被杀。如果只杀 shell，孙进程会变成孤儿继续跑。
- **stdout 和 stderr 进同一个回调**。模型看到的顺序和终端里一致，不需要分别处理。
- **超时和中止都只做一件事：杀进程树**。然后等子进程真正退出，再根据 `timedOut` 或 `signal.aborted` 抛出约定好的 `"timeout:N"` 或 `"aborted"` 错误，上层据此生成提示。
- **`trackDetachedChildPid`**。detached 子进程不会随父进程退出，pi 自己退出时要把登记过的子进程都杀掉。
- **信号退出的退出码**。被信号杀死的 shell 没有退出码（`null`），这里按 shell 惯例换成 `128 + 信号编号`，例如 SIGKILL 是 137，避免被当成成功。
- **`waitForChildProcess`**。后台孙进程可能继承了 stdout 管道一直不关，单纯等 `close` 事件会永远卡住。这个工具函数处理了这种情况。

`killProcessTree` 在 [utils/shell.ts:220-263](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/utils/shell.ts#L220-L263)：

### 7.4 OutputAccumulator：有界内存里接住任意长的输出

一条 `find /` 可能输出几百 MB。如果把全部输出存在内存里，再在结束时 `truncateTail`，内存会爆掉。`OutputAccumulator` 的思路是：内存里只保留一个“滚动的尾巴”用于显示，完整输出一旦超出上限就写进临时文件。

```ts title="packages/coding-agent/src/core/tools/output-accumulator.ts:57-78"
	constructor(options: OutputAccumulatorOptions = {}) {
		this.maxLines = options.maxLines ?? DEFAULT_MAX_LINES;
		this.maxBytes = options.maxBytes ?? DEFAULT_MAX_BYTES;
		this.maxRollingBytes = Math.max(this.maxBytes * 2, 1);
		this.tempFilePrefix = options.tempFilePrefix ?? "pi-output";
	}

	append(data: Buffer): void {
		if (this.finished) {
			throw new Error("Cannot append to a finished output accumulator");
		}

		this.totalRawBytes += data.length;
		this.appendDecodedText(this.decoder.decode(data, { stream: true }));

		if (this.tempFileStream || this.shouldUseTempFile()) {
			this.ensureTempFile();
			this.tempFileStream?.write(data);
		} else if (data.length > 0) {
			this.rawChunks.push(data);
		}
	}
```

`append` 同时维护两份数据：

1. **解码后的尾巴** `tailText`。用流式 `TextDecoder`（`stream: true`）解码，一个多字节字符被拆在两个 chunk 之间时不会产生乱码。尾巴超过 `maxRollingBytes * 2`（默认 200KB）时，`trimTail` 把它削到 100KB，并记录削掉的位置是否恰好在行首。
2. **原始字节**。没超上限时存在 `rawChunks` 数组里；一旦总量超过 50KB 或 2000 行，`ensureTempFile` 打开临时文件，把已有的 chunk 先写进去，之后所有数据直接写文件。

行数通过数换行符增量统计，不需要保存全文。`snapshot()` 对尾巴做一次 `truncateTail`，但用累计的 `totalLines`、`totalDecodedBytes` 覆盖结果里的总数，所以提示里的“共 N 行”是真实总数：

```ts title="packages/coding-agent/src/core/tools/output-accumulator.ts:91-119"
	snapshot(options: { persistIfTruncated?: boolean } = {}): OutputSnapshot {

			maxLines: this.maxLines,

		});
		const truncated = this.totalLines > this.maxLines || this.totalDecodedBytes > this.maxBytes;
		const truncatedBy = truncated
			? (tailTruncation.truncatedBy ?? (this.totalDecodedBytes > this.maxBytes ? "bytes" : "lines"))
			: null;
		const truncation: TruncationResult = {
			...tailTruncation,
			truncated,
			truncatedBy,
			totalLines: this.totalLines,
			totalBytes: this.totalDecodedBytes,
			maxLines: this.maxLines,
			maxBytes: this.maxBytes,
		};

		if (options.persistIfTruncated && truncation.truncated) {
			this.ensureTempFile();
		}

		return {
			content: truncation.content,

```

`getSnapshotText` 在尾巴不从行首开始时丢掉第一行残片，保证显示的第一行是完整的。内存占用因此有上界：尾巴最多约 200KB，原始 chunk 最多约 50KB，其余都在磁盘上。

具体例子：一个测试命令输出 8000 行后以退出码 1 结束，模型收到的是最后 2000 行，后面跟着：

```text
[Showing lines 6001-8000 of 8000. Full output: /tmp/pi-bash-xxxx.log]

Command exited with code 1
```

模型如果需要看前面的部分，可以用 read 或 `grep` 去读那个临时文件，而不用重跑命令。这是“截断但不丢失”：上下文里只放尾巴，完整内容在磁盘上随时可取。

几种结束状态的处理：

| 情况 | 结果 | 模型看到的结尾 |
| --- | --- | --- |
| 退出码 0 | 正常结果 | 输出本身，空输出时为 `(no output)` |
| 退出码非 0 | `isError: true` 的结果 | `Command exited with code N` |
| 超时 | 抛错 | 已有输出 + `Command timed out after N seconds` |
| 中止 | 抛错 | 已有输出 + `Command aborted` |
| 无退出码 | 抛错 | `Command terminated without an exit code` |

非零退出码用 `isError` 而不是抛错，这样 `structuredContent`（含 `exit_code`、`wall_time_seconds`、最多 1MB 的完整输出）能交给 codemode 脚本，脚本可以自己判断失败。超时和中止的错误里也带上了已经产生的输出，模型能看到命令卡在哪里。

```ts title="packages/coding-agent/src/core/tools/grep.ts:162-170"
						if (glob) args.push("--glob", glob);
						args.push("--", pattern, searchPath);

						const child = spawn(rgPath, args, { stdio: ["ignore", "pipe", "pipe"] });
```

- `rgPath` 来自 `ensureTool("rg")`，本机没有 ripgrep 时会自动下载。
- `--no-config` 防止用户的 ripgreprc 改变工具语义，例如用户配置了 `--smart-case`，模型传 `ignoreCase: false` 就不再可靠。
- `--json` 让每个匹配是一行结构化 JSON，文件名里有冒号也不会解析错。
- `--hidden` 搜索隐藏文件，但仍然遵守 `.gitignore`。
- `--` 之后才放 pattern，pattern 以 `-` 开头时不会被当成选项。

匹配数到 `limit`（默认 100）时立刻 `child.kill()`，不再等 ripgrep 扫完整个仓库（[grep.ts:236-239](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/tools/grep.ts#L236-L239)）。被自己杀掉的退出码不算错误（`killedDueToLimit`）；ripgrep 的退出码 1 表示“没有匹配”，也不算错误。

输出格式模仿 `grep -n`：匹配行是 `path:行号: 内容`，上下文行是 `path-行号- 内容`。每行先过 `truncateLine` 截到 500 字符，整体再过一次 `truncateHead`，这里把行数上限设成 `Number.MAX_SAFE_INTEGER`，因为条数已经由 `limit` 控制。最后汇总提示：

```ts title="packages/coding-agent/src/core/tools/grep.ts:287-305"
							// Build actionable notices for truncation and match limits.
							const notices: string[] = [];
							if (matchLimitReached) {

```

提示同样给出确切的下一步：`limit` 翻倍，或者改写 pattern，或者用 read 看完整行。

### 8.2 find：fd 与路径型 glob

find 的参数是 `pattern`（glob）、`path`、`limit`（默认 1000），底层用 fd。值得注意的是参数改写：

```ts title="packages/coding-agent/src/core/tools/find.ts:182-214"
						const args: string[] = ["--glob", "--color=never", "--hidden"];

						// fd normally ignores .gitignore outside git repos, so keep --no-require-git
						// there. Inside repos, use fd's default git-aware behavior so parent
						// .gitignore rules stop at nested repo boundaries:
						// https://github.com/earendil-works/pi/issues/5960
						let insideGitRepo = false;
						for (let current = searchPath; ; ) {
							if (await pathExists(path.join(current, ".git"))) {
								insideGitRepo = true;
								break;
							}
							const parent = path.dirname(current);
							if (parent === current) break;
							current = parent;
						}
						if (!insideGitRepo) args.push("--no-require-git");
						args.push("--max-results", String(effectiveLimit));

						// fd --glob matches against the basename unless --full-path is set; in --full-path
						// mode it matches against the absolute candidate path, so a path-containing
						// pattern like 'src/**/*.spec.ts' needs a leading '**/' to match anything.
						let effectivePattern = pattern;
						if (pattern.includes("/")) {
							args.push("--full-path");
							if (!pattern.startsWith("/") && !pattern.startsWith("**/") && pattern !== "**") {
								effectivePattern = `**/${pattern}`;
							}
							// fd matches full paths using native separators on Windows.
							if (process.platform === "win32")
								effectivePattern = effectivePattern.replaceAll("/", String.raw`[/\\]`);
						}
						args.push("--", effectivePattern, searchPath);
```

问题是：模型习惯写 `src/**/*.spec.ts` 这种带路径的 glob，但 fd 默认只拿 glob 去匹配文件名，这个 pattern 永远匹配不到。加上 `--full-path` 后 fd 改为匹配绝对路径，又需要在前面补 `**/`。这段代码替模型把参数改成 fd 能理解的形式。`.gitignore` 的处理也是同样的思路：在 git 仓库外部也希望遵守 `.gitignore`，仓库内则交给 fd 默认行为，以便嵌套仓库的边界正确。

如果扩展通过 `FindOperations.glob` 提供了自定义实现，就不调用 fd，直接用扩展的结果，后面的相对化、截断、提示逻辑共用。

### 8.3 ls

ls 最简单：`readdir`，大小写不敏感排序，对每一项 `stat`，目录加 `/` 后缀，最多 500 项（[ls.ts:99-130](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/tools/ls.ts#L99-L130)）。`stat` 失败的项（例如坏掉的符号链接）直接跳过。和 `ls` 命令不同，它总是包含点文件，模型不需要记得加 `-a`。

## 9. powershell：只换配置的 bash

powershell 没有自己的执行逻辑，它和 bash 共用 `createShellToolDefinition`，只换一份 `ShellToolConfig` 和执行后端：

```ts title="packages/coding-agent/src/core/tools/powershell.ts:16-57"
const UTF8_OUTPUT_PREFIX = "try { [Console]::OutputEncoding=[System.Text.Encoding]::UTF8 } catch {}\n";

// ...

export function createLocalPowerShellOperations(): PowerShellOperations {
	const operations = createLocalShellOperations("PowerShell", getPowerShellConfig);
	return {
		exec: (command, cwd, options) => operations.exec(`${UTF8_OUTPUT_PREFIX}${command}`, cwd, options),
	};
}

const powershellToolConfig: ShellToolConfig = {
	name: "powershell",
	label: "powershell",
	shellName: "PowerShell",
	prompt: "PS>",
	promptSnippet: powershellToolSystemPromptContribution.snippet,
	promptGuidelines: powershellToolSystemPromptContribution.guidelines,
	tempFilePrefix: "pi-powershell",
};

export function createPowerShellToolDefinition(
	cwd: string,
	options?: PowerShellToolOptions,
): ReturnType<typeof createShellToolDefinition> {
	return createShellToolDefinition(cwd, powershellToolConfig, {
		...options,
		operations: options?.operations ?? createLocalPowerShellOperations(),
	});
}
```

唯一的特殊处理是在每条命令前加一句设置 `[Console]::OutputEncoding` 为 UTF-8。Windows 上 PowerShell 默认用本地代码页输出，不设置的话中文路径、错误信息会变成乱码。截断、超时、杀进程树、临时文件这些全部和 bash 一样。这个复用说明 `createShellToolDefinition` 的抽象边界选得合适：shell 之间的差异只在“用哪个可执行文件、命令前面加什么”。

## 小结

- 内置工具和扩展工具共用 `ToolDefinition` 接口。`wrapToolDefinition` 只把 agent-core 认识的字段传下去，并负责注入 `ctx`；没有 `ctx` 时工具退回创建时的 cwd。
- `index.ts` 为每个工具提供 Definition 和 Tool 两种工厂，并按用途分组；AgentSession 建出全部八个，默认激活 read、bash、edit、write。
- 每个工具的 IO 都抽成可替换的 Operations 接口，远程执行只需换 Operations。
- 截断有两道上限（2000 行、50KB），谁先到算谁。read 和搜索类工具保留开头，bash 保留结尾。每条截断提示都包含下一步要用的确切参数。
- read 用 `offset/limit` 分页；图片按当前模型的尺寸限制缩放；路径解析会尝试 macOS 截图文件名的几种变体。
- edit 用文本替换而不是行号。先精确匹配，失败再做有限的宽松匹配；找不到、多处匹配、重叠、无变化都直接报错，所有检查在写文件之前完成。宽松匹配时只改动真正编辑的行。
- 工具默认并行执行，`withFileMutationQueue` 按 realpath 对同一文件的写操作排队；写入类工具在每个 `await` 之后检查中止，不在中止事件里提前释放队列。
- bash 用 detached 进程组，超时和中止都杀整个进程树；`OutputAccumulator` 内存里只保留滚动尾巴，超限后完整输出写入临时文件，路径告诉模型。
- powershell 复用 bash 的全部实现，只换 shell 配置和 UTF-8 前缀。
