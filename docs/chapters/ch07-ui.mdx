## 1. 问题：界面层要解决什么

第 3 章讲过，pi 的核心是 AgentSession：它包装 Agent，负责 prompt、排队、compaction、扩展和持久化，对外只暴露两样东西：方法（`prompt`、`steer`、`abort` 等）和事件（`subscribe`）。界面层要做的事情可以归结为两条：

1. 把用户输入变成 AgentSession 的方法调用。
2. 把 AgentSession 的事件变成用户能看到的输出。

不同场景对“输入从哪来、输出到哪去”的要求不同：

| 模式 | 输入 | 输出 | 入口 |
| --- | --- | --- | --- |
| 交互模式 | 终端键盘 | 终端界面（pi-tui） | [interactive-mode.ts](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/modes/interactive/interactive-mode.ts) |
| print 模式 | 命令行参数、stdin | 最后一条回复的文本，或 JSON 事件流 | [print-mode.ts](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/modes/print-mode.ts) |
| RPC 模式 | stdin 上的 JSONL 命令 | stdout 上的 JSONL 响应和事件 | [modes/rpc/](https://github.com/earendil-works/pi/tree/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/modes/rpc) |
| SDK | TypeScript 函数调用 | `session.subscribe` 回调 | `createAgentSession()` |

[main.ts](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/main.ts#L112-L123) 按参数和终端状态选模式：

## 2. pi-tui 的组件模型

### 2.1 render(width) → string[]

pi-tui（`packages/tui`）是一个独立的终端 UI 库。它的组件接口非常小：

```ts title="packages/tui/src/tui.ts:117-142"
export interface Component {
	/**
	 * Render the component to lines for the given viewport width
	 * @param width - Current viewport width
	 * @returns Array of strings, each representing a line
	 */
	render(width: number): string[];

	/** Optional handler for keyboard input when component has focus. */
	handleInput?(data: string): void;

	/** Optional normalized mouse handler. */
	handleMouse?(event: TuiMouseEvent): TuiMouseEventResult | undefined;

	/**
	 * If true, component receives key release events (Kitty protocol).
	 * Default is false - release events are filtered out.
	 */
	wantsKeyRelease?: boolean;

	/**
	 * Invalidate any cached rendering state.
	 * Called when theme changes or when component needs to re-render from scratch.
	 */
	invalidate(): void;
}
```

`render(width)` 拿到可用宽度，返回一个字符串数组，每个元素是终端上的一行。字符串里可以带 ANSI 转义序列（控制颜色、粗体等的不可见字符），但**可见宽度**不能超过 `width`。没有布局引擎，没有虚拟 DOM，也没有坐标：组件只回答“在这个宽度下我长什么样”。

这个设计的好处是组件很容易写、很容易测试：给一个宽度，断言返回的行就行。代价是性能完全靠组件自己缓存，以及渲染器在下游做差分（第 3 节）。

最简单的组件 `Text`：

```ts title="packages/tui/src/components/text.ts:50-112"
	render(width: number): string[] {
		// Check cache
		if (this.cachedLines && this.cachedText === this.text && this.cachedWidth === width) {
			return this.cachedLines;
		}
		// ...
		// Replace tabs with 3 spaces
		const normalizedText = this.text.replace(/\t/g, "   ");

		// Reduce margins when necessary so content and padding fit within the available width.
		const paddingX = Math.min(this.paddingX, Math.max(0, Math.floor((width - 1) / 2)));
		const contentWidth = Math.max(1, width - paddingX * 2);

		// Wrap text (this preserves ANSI codes but does NOT pad)
		const wrappedLines = wrapTextWithAnsi(normalizedText, contentWidth);

		// Add margins and background to each line
		const leftMargin = " ".repeat(paddingX);
		const rightMargin = " ".repeat(paddingX);
		const contentLines: string[] = [];

		for (const line of wrappedLines) {
		// ...
		const result = [...emptyLines, ...contentLines, ...emptyLines];
		flattenLines(result);

		// Update cache
		this.cachedText = this.text;
		this.cachedWidth = width;
		this.cachedLines = result;

		return result.length > 0 ? result : [""];
	}
```

两个要点：

- **缓存**：文本和宽度都没变时直接返回上次的数组。交互模式里聊天记录可能有几百个组件，每帧都会对它们调用 `render`，缓存让没变化的组件几乎零开销。`invalidate()` 清缓存，主题切换时会对所有组件调用它。
- **补齐宽度**：每行用空格补到 `width`。这样新内容覆盖旧内容时，不会留下上一帧更长那一行的残字。

### 2.2 Container：把子组件的行拼起来

```ts title="packages/tui/src/tui.ts:405-417"
	render(width: number): string[] {
		const lines: string[] = [];
		const mouseChildren: Array<{ component: Component; height: number }> = [];
		for (const child of this.children) {
			const childLines = child.render(width);
			mouseChildren.push({ component: child, height: childLines.length });
			for (const line of childLines) {
				lines.push(line);
			}
		}
		this.mouseLayout = { width, children: mouseChildren };
		return lines;
	}
```

`Container` 依次渲染子组件，把行首尾相接。整个界面就是一棵 Container 树，根节点 `TUI` 本身也继承自 `Container`（`TuiBase extends Container`，[tui.ts:506](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/tui/src/tui.ts#L506)）。所谓布局就是“从上往下排”。顺便记下每个子组件占几行，供鼠标事件按行号找到目标组件。

### 2.3 焦点、光标与输入

键盘输入只发给一个组件：`tui.setFocus(component)` 指定的那个，调用它的 `handleInput(data)`。`data` 是终端发来的原始字节序列，比如回车是 `"\r"`，上箭头是 `"\x1b[A"`。

光标位置也用字符串表达。获得焦点的组件在输出里光标所在位置插入一个零宽标记：

```ts title="packages/tui/src/tui.ts:174-196"
/**
 * Interface for components that can receive focus and display a hardware cursor.
 * When focused, the component should emit CURSOR_MARKER at the cursor position
 * in its render output. TUI will find this marker and position the hardware
 * cursor there for proper IME candidate window positioning.
 */
export interface Focusable {
	/** Set by TUI when focus changes. Component should emit CURSOR_MARKER when true. */
	focused: boolean;
}

/** Type guard to check if a component implements Focusable */
export function isFocusable(component: Component | null): component is Component & Focusable {
	return component !== null && "focused" in component;
}

/**
 * Cursor position marker - APC (Application Program Command) sequence.
 * This is a zero-width escape sequence that terminals ignore.
 * Components emit this at the cursor position when focused.
 * TUI finds and strips this marker, then positions the hardware cursor there.
 */
export const CURSOR_MARKER = "\x1b_pi:c\x07";
```

APC（Application Program Command）是一类终端会忽略的转义序列，所以这个标记不会显示出来。渲染器在最终输出里找到它，算出行列号，删掉标记，再把真实的终端光标移过去。为什么要移动真实光标？因为中文、日文输入法的候选窗口跟随硬件光标，光标位置不对，候选窗就会出现在屏幕角落。编辑器里的用法：

```ts title="packages/tui/src/components/editor.ts:577-592"
			// Add cursor if this line has it
			if (layoutLine.hasCursor && layoutLine.cursorPos !== undefined) {
				const before = displayText.slice(0, layoutLine.cursorPos);
				const after = displayText.slice(layoutLine.cursorPos);

				// Hardware cursor marker (zero-width, emitted before fake cursor for IME positioning)
				const marker = emitCursorMarker ? CURSOR_MARKER : "";

				if (after.length > 0) {

					const firstGrapheme = afterGraphemes[0]?.segment || "";
					const restAfter = after.slice(firstGrapheme.length);
					const cursor = renderFakeCursor(firstGrapheme);

```

`marker` 放在“假光标”（一个反色显示的字符）前面：用户看到的是假光标，输入法看到的是硬件光标，两者在同一个位置。

## 3. 差分渲染

### 3.1 什么时候渲染

组件状态变了就调用 `tui.requestRender()`。它不立即渲染，而是合并到下一帧：

```ts title="packages/tui/src/tui.ts:1027-1079"
	requestRender(force = false): void {
		if (force) {
			this.resetRenderState();
			this.requestImmediateRender();
			return;
		}
		if (this.renderRequested) return;
		this.renderRequested = true;
		process.nextTick(() => this.scheduleRender());
	}
	// ...
	private scheduleRender(): void {
		if (this.stopped || this.renderTimer || !this.renderRequested) {
			return;
		}
		const elapsed = performance.now() - this.lastRenderAt;
		const delay = Math.max(0, TuiBase.MIN_RENDER_INTERVAL_MS - elapsed);
		this.renderTimer = setTimeout(() => {
			this.renderTimer = undefined;
			if (this.stopped || !this.renderRequested) {
				return;
			}
			this.renderRequested = false;
			this.lastRenderAt = performance.now();
			this.doRender();
			if (this.renderRequested) {
				this.scheduleRender();
			}
		}, delay);
	}
```

- 同一个 tick 内多次 `requestRender()` 只算一次（`renderRequested` 标志）。
- 两帧之间至少间隔 16ms（`MIN_RENDER_INTERVAL_MS`），约 60 帧每秒。模型每秒推几十个 token，每个 token 一次 `message_update`，如果每次都写终端，终端会被刷爆；节流后多个 token 合并成一帧。
- `force` 参数清空渲染状态，立即全量重绘。

### 3.2 两种渲染器

`TuiBase` 的 `doRender()` 是抽象方法，有两个实现：

| 实现 | 模式 | 特点 |
| --- | --- | --- |
| `TuiMainScreen` | 默认（regular） | 在终端主屏上输出，历史进入终端自己的回滚缓冲区，可以用终端原生的滚动和搜索 |
| `TuiAltScreen` | fullscreen | 切到备用屏幕（`\x1b[?1049h`），自己管理滚动、搜索、鼠标选择，每帧按屏幕坐标写行 |

coding-agent 在 [tui-renderer.ts](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/modes/interactive/tui-renderer.ts#L22-L50) 里按 `tuiMode` 二选一：

### 3.3 一帧的流程

```ts title="packages/tui/src/tui-main-screen.ts:247-275"
	protected doRender(): void {
		if (this.stopped) return;
		const width = this.terminal.columns;
		const height = this.terminal.rows;
		const widthChanged = this.previousWidth !== 0 && this.previousWidth !== width;
		const heightChanged = this.previousHeight !== 0 && this.previousHeight !== height;
		const previousBufferLength = this.previousHeight > 0 ? this.previousViewportTop + this.previousHeight : height;
		let prevViewportTop = heightChanged ? Math.max(0, previousBufferLength - height) : this.previousViewportTop;
		let viewportTop = prevViewportTop;
		let hardwareCursorRow = this.hardwareCursorRow;
		const computeLineDiff = (targetRow: number): number => {
			const currentScreenRow = hardwareCursorRow - prevViewportTop;
			const targetScreenRow = targetRow - viewportTop;
			return targetScreenRow - currentScreenRow;
		};

		// Render all components to get new lines
		// Resolve fake cursors before compositing so overlays and line slicing see plain SGR codes
		let newLines = this.resolveFakeCursors(this.render(width));

		// Composite overlays into the rendered lines (before differential compare)
		if (this.hasOverlayEntries) {
			newLines = this.compositeOverlays(newLines, width, height);
		}

		// Extract cursor position before applying line resets (marker must be found first)
		const cursorPos = this.extractCursorPosition(newLines, height);

		newLines = this.applyLineResets(newLines);
```

1. 从根节点 `render(width)` 得到完整的行数组 `newLines`。
2. 把浮层（overlay，比如选择框）合成进这些行。
3. 找出光标标记的位置并删掉标记。
4. 和上一帧的 `previousLines` 比较，决定怎么写终端。

某些情况下没法差分，只能全量重绘：

```ts title="packages/tui/src/tui-main-screen.ts:331-352"
		// First render - just output everything without clearing (assumes clean screen)
		if (this.previousLines.length === 0 && !widthChanged && !heightChanged) {
			logRedraw("first render");
			fullRender(false);
			return;
		}

		// Width changes always need a full re-render because wrapping changes.
		if (widthChanged) {
			logRedraw(`terminal width changed (${this.previousWidth} -> ${width})`);
			fullRender(true);
			return;
		}

		// Height changes normally need a full re-render to keep the visible viewport aligned,
		// but Termux changes height when the software keyboard shows or hides.
		// In that environment, a full redraw causes the entire history to replay on every toggle.
		if (heightChanged && !isTermuxSession()) {
			logRedraw(`terminal height changed (${this.previousHeight} -> ${height})`);
			fullRender(true);
			return;
		}
```

宽度变了，每一行的折行都会变，只能整体重画（`\x1b[2J\x1b[H\x1b[3J`：清屏、光标回左上角、清回滚缓冲区）。高度变了也一样，但 Termux（安卓上的终端）例外：软键盘弹出收起都会改变高度，每次都全量重绘会把整段历史重放一遍。

### 3.4 找出变化的行

```ts title="packages/tui/src/tui-main-screen.ts:363-398"
		// Find first and last changed lines
		let firstChanged = -1;
		let lastChanged = -1;
		const maxLines = Math.max(newLines.length, this.previousLines.length);
		for (let i = 0; i < maxLines; i++) {
			const oldLine = i < this.previousLines.length ? this.previousLines[i] : "";
			const newLine = i < newLines.length ? newLines[i] : "";

			if (oldLine !== newLine) {
				if (firstChanged === -1) {
					firstChanged = i;
				}
				lastChanged = i;
			}
		}
		const appendedLines = newLines.length > this.previousLines.length;
		if (appendedLines) {
			if (firstChanged === -1) {
				firstChanged = this.previousLines.length;
			}
			lastChanged = newLines.length - 1;
		}
		if (firstChanged !== -1) {
			const expandedRange = this.expandChangedRangeForKittyImages(firstChanged, lastChanged, newLines);
			firstChanged = expandedRange.firstChanged;
			lastChanged = expandedRange.lastChanged;
		}
		const appendStart = appendedLines && firstChanged === this.previousLines.length && firstChanged > 0;

		// No changes - but still need to update hardware cursor position if it moved
		if (firstChanged === -1) {
			this.positionHardwareCursor(cursorPos, newLines.length);
			this.previousViewportTop = prevViewportTop;
			this.previousHeight = height;
			return;
		}
```

逐行比较字符串，记下第一个和最后一个不同的行号。因为组件有缓存，没变化的行是同一个字符串对象，比较很快。完全没变化时，只更新光标位置，不写任何内容。

具体例子：模型正在输出一段回复，屏幕上有 40 行。这一帧新到了几个 token，只影响助手消息的最后一行（第 37 行），底部的编辑器和状态栏不变。比较结果是 `firstChanged = lastChanged = 37`，渲染器只需要：把光标移到第 37 行、清掉这一行、写入新内容。其余 39 行一个字节都不发。

### 3.5 只重写变化的范围

```ts title="packages/tui/src/tui-main-screen.ts:450-547"
		// Differential rendering can only touch what was actually visible.
		// If the first changed line is above the previous viewport, we need a full redraw.
		if (firstChanged < prevViewportTop) {
			logRedraw(`firstChanged < viewportTop (${firstChanged} < ${prevViewportTop})`);
			fullRender(true);
			return;
		}

		// Render from first changed line to end
		// Keep updates wrapped in synchronized output while writing bounded chunks.
		const output = new BoundedTerminalWriter((data) => this.terminal.write(data));
		output.append("\x1b[?2026h"); // Begin synchronized output
		output.append(this.deleteChangedKittyImages(firstChanged, lastChanged));
		const prevViewportBottom = prevViewportTop + height - 1;
		const moveTargetRow = appendStart ? firstChanged - 1 : firstChanged;
		if (moveTargetRow > prevViewportBottom) {
			const currentScreenRow = Math.max(0, Math.min(height - 1, hardwareCursorRow - prevViewportTop));
			const moveToBottom = height - 1 - currentScreenRow;
			if (moveToBottom > 0) {
				output.append(`\x1b[${moveToBottom}B`);
			}
			const scroll = moveTargetRow - prevViewportBottom;
			output.append("\r\n".repeat(scroll));
			prevViewportTop += scroll;
			viewportTop += scroll;
			hardwareCursorRow = moveTargetRow;
		}

		// Move cursor to first changed line (use hardwareCursorRow for actual position)
		const lineDiff = computeLineDiff(moveTargetRow);
		if (lineDiff > 0) {
			output.append(`\x1b[${lineDiff}B`); // Move down
		} else if (lineDiff < 0) {
			output.append(`\x1b[${-lineDiff}A`); // Move up
		}

		output.append(appendStart ? "\r\n" : "\r"); // Move to column 0

		// Only render changed lines (firstChanged to lastChanged), not all lines to end
		// This reduces flicker when only a single line changes (e.g., spinner animation)
		const renderEnd = Math.min(lastChanged, newLines.length - 1);
		for (let i = firstChanged; i <= renderEnd; i++) {
			if (i > firstChanged) output.append("\r\n");
			// ...
			output.append("\x1b[2K"); // Clear current line
			if (!isImage && visibleWidth(line) > width) {
			// ...
			output.append(line);
		}
```

用到的转义序列：

| 序列 | 含义 |
| --- | --- |
| `\x1b[nA` / `\x1b[nB` | 光标上移 / 下移 n 行 |
| `\r` | 回到行首 |
| `\x1b[2K` | 清除当前整行 |
| `\x1b[?2026h` / `\x1b[?2026l` | 开始 / 结束同步输出 |

渲染器记录了硬件光标当前在哪一行（`hardwareCursorRow`），用相对移动走到 `firstChanged`，然后逐行“清行 + 写入”，直到 `lastChanged`。注释里说得很直接：只渲染 `firstChanged` 到 `lastChanged`，而不是到末尾，为的是一个 spinner 动画这样的单行变化不引起闪烁。

开头那个判断是主屏模式的根本限制：**已经滚出屏幕顶端、进入回滚缓冲区的行，终端不允许再修改**。如果变化发生在可视区域上方（`firstChanged < prevViewportTop`），差分无从下手，只能全量重绘。这种情况在正常对话中很少发生，因为新内容总是追加在底部。

渲染器对组件有一个硬性检查：某一行的可见宽度超过终端宽度时，直接停止 TUI 并抛错，同时把所有行写进崩溃日志：


### 3.6 CSI 2026：同步输出

CSI（Control Sequence Introducer）指以 `ESC [` 开头的一类终端控制序列。`\x1b[?2026h` 和 `\x1b[?2026l` 是其中的一对，开启和关闭 DEC 私有模式 2026，名字叫 Synchronized Output（同步输出）。

问题是这样的：一次差分更新要发好几段内容，“上移 3 行、清行、写第一行、换行、清行、写第二行……”。终端收到数据就会开始绘制，如果正好在“清行”之后、“写入”之前刷新了一次屏幕，用户就会看到一行短暂变空，这就是闪烁。全量重绘更明显：清屏之后到内容写完之前，整个屏幕可能闪一下白。

同步输出的语义是：收到 `?2026h` 后，终端照常解析后续数据、更新内部的屏幕缓冲区，但**暂停把缓冲区画到屏幕上**；收到 `?2026l` 后，一次性把最终结果画出来。用户只会看到“更新前”和“更新后”两个状态。不支持这个模式的终端会忽略这两个序列，行为退化为普通输出，不会出错。

pi-tui 的每一条写入路径都包在这一对序列里：全量重绘（`fullRender`）、只删除行、差分更新，以及 `TuiAltScreen` 的每一帧：

```ts title="packages/tui/src/tui-alt-screen.ts:1743-1791"

		if (fullRedraw) {

			buffer += this.getShowHardwareCursor() ? "\x1b[?25h" : "\x1b[?25l";

```

备用屏幕的写法更直接：用 `\x1b[行;列H` 绝对定位，逐行比较 `screen[row]` 和 `previousScreen[row]`，只重写不同的行，整帧拼成一个字符串，一次 `write`。

主屏渲染器则用 `BoundedTerminalWriter` 以 1 MiB 为单位分块写（[tui-main-screen.ts:11-74](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/tui/src/tui-main-screen.ts#L11-L74)）：长会话首次全量渲染可能产生非常大的输出，拼成一个字符串会超出 V8 的字符串长度上限。分块不影响同步输出，因为开始和结束序列分别在第一块和最后一块里。

输入框是 pi-tui 里最复杂的组件（[editor.ts](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/tui/src/components/editor.ts)，约 2.5k 行）。它要处理多行编辑、自动补全、粘贴、撤销、历史、Emacs 风格的 kill ring（删除的文本存入一个环，可以再贴回来）、按字符跳转等。

### 4.3 粘贴

终端支持 bracketed paste 模式：粘贴的内容被包在 `\x1b[200~` 和 `\x1b[201~` 之间，程序可以把它和逐字敲入区分开（[editor.ts:720-744](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/tui/src/components/editor.ts#L720-L744)）。没有这个区分，粘贴一段多行代码时，第一个换行就会被当作回车提交。

### 6.2 streamingBehavior：steer 还是 followUp

模型正在输出时，用户又输入了一句话。这句话有两种处理方式（第 2 章讲过 agent 循环这一侧）：

- **steer**（插话）：当前 turn 的工具执行完后、下一次调用模型前注入。适合“停一下，别改那个文件”。
- **followUp**（排队）：等 agent 把这一轮全部做完，再作为新的输入发送。适合“做完以后顺便跑一下测试”。

交互模式里，普通回车是 steer；`app.message.followUp` 快捷键（默认 Alt+Enter，Windows 上是 Ctrl+Q）是 followUp：

```ts title="packages/coding-agent/src/modes/interactive/interactive-mode.ts:3462-3562"
					this.streamingComponent.updateContent(this.streamingMessage, true);

					for (const content of this.streamingMessage.content) {
						if (content.type === "toolCall") {
							if (!this.pendingTools.has(content.id)) {
								const component = new ToolExecutionComponent(
									content.name,
									content.id,
									content.arguments,
									{
										showImages: this.settingsManager.getShowImages(),
										imageWidthCells: this.settingsManager.getImageWidthCells(),
										outputPad: this.outputPad,
									},
									this.getRegisteredToolDefinition(content.name),
									this.ui,
									this.sessionManager.getCwd(),
								);
								component.setExpanded(this.toolOutputExpanded);
								this.chatContainer.addChild(component);
								this.pendingTools.set(content.id, component);
							} else {
								const component = this.pendingTools.get(content.id);
								if (component) {
									component.updateArgs(content.arguments);
								}
							}
						}
					}
					this.ui.requestRender();
				}
				break;

			case "message_end":
				if (event.message.role === "user") break;
				if (this.streamingComponent && event.message.role === "assistant") {
					// ...
					this.streamingComponent.updateContent(this.streamingMessage, false);
					// ...
					} else {
						// Args are now complete - trigger diff computation for edit tools
						for (const [, component] of this.pendingTools.entries()) {
							component.setArgsComplete();
						}
						this.maybeShowThinkingDropNotice(this.streamingMessage);
						this.maybeShowCacheMissNotice(this.streamingMessage);
					}
					this.streamingComponent = undefined;
					this.streamingMessage = undefined;
					this.footer.invalidate();
				}
				this.ui.requestRender();
				break;
```

一条助手消息在界面上的生命周期：

1. `message_start`：创建一个 `AssistantMessageComponent`，挂到 `chatContainer` 末尾，记为 `streamingComponent`。
2. `message_update`：每个增量都调用 `updateContent(message, true)` 重设内容，然后 `requestRender()`。消息里出现新的 `toolCall` 块时，立刻创建 `ToolExecutionComponent` 挂在后面，参数还在流式生成时就能看到工具调用框。
3. `message_end`：最后一次更新，`isStreaming` 为 `false`；把各工具组件标记为参数完整（edit 工具此时才计算 diff）。

工具执行相关的部分：


这里能看到整个设计的分工：AgentSession 不知道界面长什么样，只发事件；交互模式不知道 agent 循环怎么跑，只根据事件增删、更新组件，再 `requestRender()`；pi-tui 不知道什么是消息，只把组件树渲染成行、做差分、写终端。每层只依赖下一层的接口。

print 模式（`pi -p "..."`，或 stdin/stdout 不是终端时）发完提示就退出：

和交互模式一样是 `bindExtensions` + `subscribe` + `prompt`，只是：

- 不传 `uiContext`，扩展拿到 `noOpUIContext`，`ctx.hasUI` 为 `false`。
- `--mode json` 时，每个事件序列化成一行 JSON 写到 stdout；否则什么都不输出，最后只打印最后一条助手消息的文本。
- 每个 `prompt()` 都 await 到 agent 完全结束，再发下一条。没有并发输入，所以不需要 `streamingBehavior`。

JSON 输出不是原样序列化事件。`message_update` 里带着累积到当前为止的整条消息（`partial`），原样输出的话，一条 1 万 token 的回复会产生上千行、总量平方增长的输出。`toJsonEvent` 把它去掉，只留增量：

```ts title="packages/coding-agent/src/modes/json-event.ts:40-61"

 * Remove cumulative assistant snapshots from streaming wire events.
 * `message_start` provides the initial message, deltas build it, and
 * `message_end` provides the final authoritative message. Cumulative usage,

		return event;
	}
	if (event.message.role !== "assistant") {
		throw new Error("message_update message is not an assistant message");
```

消费者用 `message_start` 拿到初始消息，用增量拼出过程，用 `message_end` 拿到最终的完整消息。第 6 章的 subagent 示例就是这样读子进程输出的：它只关心 `message_end`。

## 8. RPC 模式：JSONL 协议

### 8.1 帧格式

RPC 模式（`pi --mode rpc`）让其他程序（编辑器插件、桌面应用、其他语言写的工具）通过 stdin/stdout 驱动 pi。协议是 JSONL：每条消息是一个 JSON 对象，以 `\n` 结尾。

```ts title="packages/coding-agent/src/modes/rpc/jsonl.ts:4-41"
/**
 * Serialize a single strict JSONL record.
 *
 * Framing is LF-only. Payload strings may contain other Unicode separators such as
 * U+2028 and U+2029. Clients must split records on `\n` only.
 */
export function serializeJsonLine(value: unknown): string {
	return `${JSON.stringify(value)}\n`;
}

/**
 * Attach an LF-only JSONL reader to a stream.
 *
 * This intentionally does not use Node readline. Readline splits on additional
 * Unicode separators that are valid inside JSON strings and therefore does not
 * implement strict JSONL framing.
 */
export function attachJsonlLineReader(stream: Readable, onLine: (line: string) => void): () => void {
	const decoder = new StringDecoder("utf8");
	let buffer = "";

	const emitLine = (line: string) => {
		onLine(line.endsWith("\r") ? line.slice(0, -1) : line);
	};

	const onData = (chunk: string | Buffer) => {
		buffer += typeof chunk === "string" ? chunk : decoder.write(chunk);

		while (true) {
			const newlineIndex = buffer.indexOf("\n");
			if (newlineIndex === -1) {
				return;
			}

			emitLine(buffer.slice(0, newlineIndex));
			buffer = buffer.slice(newlineIndex + 1);
		}
	};
```

注释解释了为什么不用 Node 的 `readline`：readline 除了 `\n` 还会在 U+2028、U+2029 等 Unicode 行分隔符处切分，而这些字符在 JSON 字符串里是合法的。模型输出里恰好有这些字符时，readline 会把一条消息切成两半，导致解析失败。所以 pi 自己实现了只按 `\n` 切分的读取器。

### 8.3 prompt 命令的处理

```ts title="packages/coding-agent/src/modes/rpc/rpc-mode.ts:394-419"
			case "prompt": {

				// prompt preflight succeeds. Queued and immediately handled prompts also count as success.
				let preflightSucceeded = false;

						images: command.images,

						},
					})
					.catch((e) => {
						if (!preflightSucceeded) {
							output(error(id, "prompt", e.message));
						}
					});
				return undefined;
```

`prompt` 的处理有一个细节：不能等 `session.prompt()` 完成再回复，因为它要等整个 agent 运行结束，可能几分钟；也不能一收到就回复成功，因为模型没配置、API key 缺失这类错误要在开始运行前报告。所以 AgentSession 提供了 `preflightResult` 回调：前置检查通过、确定了去向（开始运行、进队列、被扩展命令或 `input` 事件处理掉）时立即回调，RPC 此时输出成功响应；如果前置检查就失败，`.catch` 输出错误响应。`source: "rpc"` 会传给扩展的 `input` 事件。

RPC 模式和交互模式的绑定方式相同：


## 9. SDK：直接用 AgentSession

前面三种模式都是 CLI 进程里的“壳”。如果宿主本身就是 Node 或 Bun 程序，可以跳过 CLI，直接创建 AgentSession：

```ts title="packages/coding-agent/docs/sdk.md:8-17"
import { createAgentSession } from "@earendil-works/pi-coding-agent";

const { session } = await createAgentSession();

try {
  await session.prompt("What files are in the current directory?");
  console.log(session.getLastAssistantText());
} finally {
  session.dispose();
}
```

`createAgentSession()`（[sdk.ts:191](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/sdk.ts#L191)）就是 CLI 启动时用的同一个函数（第 3 章），只是由调用者传入选项。拿到 `session` 后：

- `session.subscribe(fn)` 收到的事件和交互模式、RPC 模式收到的完全一样。
- `session.prompt(text, { streamingBehavior })`、`session.steer()`、`session.followUp()`、`session.abort()` 和其他模式调用的是同一组方法。
- 需要扩展 UI 时调用 `session.bindExtensions({ uiContext, ... })`，提供自己的 `ExtensionUIContext` 实现，和 RPC 模式的做法一样。

把四种模式放在一起看：

| | 交互 | print | RPC | SDK |
| --- | --- | --- | --- | --- |
| 输入来源 | 编辑器 `onSubmit` | 参数、stdin | stdin 上的 JSONL 命令 | 函数调用 |
| 调用的方法 | `session.prompt` | `session.prompt` | `session.prompt`、`steer`、`followUp` 等 | 同左 |
| 事件去向 | `handleEvent` 更新组件 | JSON 行或丢弃 | stdout 上的 JSON 行 | 调用者的回调 |
| 扩展 UI | 真实对话框和组件 | 无 | `extension_ui_request` | 调用者实现 |

四种模式里都没有 agent 逻辑：排队、扩展事件、compaction、重试、持久化全在 AgentSession 里。这就是第 3 章说 AgentSession 是核心的原因，也是 pi 能同时提供 TUI、脚本模式、嵌入协议和库四种形态而不重复实现的原因。

## 小结

- pi-tui 的组件接口是 `render(width)` 返回字符串数组；`Container` 把子组件的行首尾相接，界面就是一棵组件树。组件自己缓存渲染结果。
- `requestRender()` 合并同一 tick 的请求，并限制最多约 60 帧每秒。
- `TuiMainScreen` 每帧和上一帧逐行比较，只重写 `firstChanged` 到 `lastChanged` 之间的行；宽度变化、变化落在可视区上方等情况才全量重绘；超宽行直接报错。
- 所有写入都包在 CSI 2026 同步输出里，终端在整帧写完后才刷新屏幕，避免闪烁；不支持的终端会忽略它。
- 编辑器用逻辑行存储文本，提交时调用 `onSubmit`；硬件光标通过零宽 APC 标记定位，服务输入法；大段粘贴折叠成标记。
- 交互模式订阅 AgentSessionEvent，在 `message_start/update/end` 和 `tool_execution_*` 上创建、更新组件；输入在 agent 运行时以 `steer`（回车）或 `followUp`（Alt+Enter）调用 `session.prompt`。
- print 模式输出最终文本或 JSON 事件流；RPC 模式用严格按 `\n` 分帧的 JSONL 协议，扩展 UI 变成请求和响应；SDK 直接使用 AgentSession。四者共用同一个 AgentSession。
