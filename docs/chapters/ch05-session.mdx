## 1. 问题：线性的消息数组不够用

agent-core 的 `Agent` 只有一个 `state.messages` 数组。如果会话也只存一个数组，有三件事很难做：

1. **回到旧位置重来。** 用户在第 5 条消息处觉得方向错了，想从第 3 条重新问。截断数组会丢掉第 4、5 条，以后想回去看就没了。
2. **压缩上下文。** 上下文太长要把旧消息换成摘要。直接改数组会丢掉原始记录，出了问题无法追查。
3. **崩溃安全。** 每次保存都重写整个文件，写到一半崩溃，整个会话就损坏了。

pi 的方案是把会话做成**只追加的树**：

- 文件是 JSONL（每行一个 JSON 对象），新内容只追加到文件末尾。
- 每条 entry 有 `id` 和 `parentId`，所有 entry 组成一棵树。
- 有一个“叶子指针” `leafId`，指向当前位置。新 entry 的 `parentId` 就是当前 `leafId`，追加后叶子前移。
- 发给模型的上下文由“从叶子走回根”的路径计算出来。

这三条规则决定了本章的所有机制：回到旧节点只是移动叶子指针，之后的追加自然形成新分支；compaction 只是追加一条特殊 entry，在计算路径时把旧消息替换成摘要；追加写入一行，崩溃最多丢最后一行。

## 2. 数据模型：header 与 entry

### 2.1 文件头和公共字段


文件第一行永远是 `SessionHeader`：会话 id（uuidv7）、创建时间、工作目录 `cwd`、版本号，以及 fork 出来的会话指向父会话文件的 `parentSession`。header 不参与树结构，它没有 `parentId`。

之后每一行都是一个 `SessionEntry`，公共字段只有四个：`type`、`id`、`parentId`、`timestamp`。根 entry 的 `parentId` 是 `null`。

entry 的 `id` 是 8 位十六进制短 id，生成时检查是否冲突：

```ts title="packages/coding-agent/src/core/session-manager.ts:276-284"
/** Generate a unique short ID (8 hex chars, collision-checked) */
function generateId(byId: { has(id: string): boolean }): string {
	for (let i = 0; i < 100; i++) {
		const id = randomUUID().slice(0, 8);
		if (!byId.has(id)) return id;
	}
	// Fallback to full UUID if somehow we have collisions
	return randomUUID();
}
```

用短 id 是因为 id 会出现在 TUI 的树选择器、扩展 API 和日志里，8 位足够在一个会话内唯一，又便于人读。

### 2.2 全部 entry 类型


| type | 关键字段 | 进入模型上下文吗 | 用途 |
| --- | --- | --- | --- |
| `message` | `message: AgentMessage` | 是 | user、assistant、toolResult、system、bashExecution 等消息 |
| `thinking_level_change` | `thinkingLevel` | 否，但决定思考级别 | 切换 thinking 级别 |
| `model_change` | `provider`、`modelId` | 否，但决定模型 | 切换模型 |
| `usage` | `kind`、`usage` | 否 | 记录不属于对话的 token 消耗，例如缓存预热 |
| `compaction` | `summary`、`firstKeptEntryId`、`tokensBefore` | 是，变成摘要消息 | 上下文压缩检查点 |
| `branch_summary` | `fromId`、`summary` | 是，变成摘要消息 | 离开分支时的摘要 |
| `custom` | `customType`、`data` | 否 | 扩展存自己的状态 |
| `custom_message` | `customType`、`content`、`display` | 是，变成 user 消息 | 扩展往上下文里注入内容 |
| `context_edit` | `targetId`、`replacement` | 间接，修改目标 entry 的贡献 | 只追加地“编辑”早先的消息 |
| `label` | `targetId`、`label` | 否 | 给 entry 打书签 |
| `session_info` | `name` | 否 | 会话显示名 |

几点说明：

- `custom` 和 `custom_message` 的区别是“进不进上下文”。扩展保存内部状态用 `custom`，重新加载会话时扫描自己的 `customType` 恢复状态；要让模型看到的内容用 `custom_message`。
- `context_edit` 是“只追加”原则下的编辑手段：不修改目标 entry，而是追加一条 edit，投影时用 `replacement` 替换目标的内容，`replacement` 为 `null` 表示从上下文里删掉。它只在当前分支上生效。
- `label` 也是树上的普通节点（有 `parentId`），书签信息在加载时汇总到 `labelsById`。

compaction entry 的结构是本章的重点之一：

```ts title="packages/coding-agent/src/core/session-manager.ts:91-116"

	fromId: string;
	summary: string;
```

`firstKeptEntryId` 记录“从哪条 entry 开始原样保留”，它之前的消息由 `summary` 代替。`systemMessage` 保存压缩那一刻的系统提示和工具状态，因为压缩后旧的 system 消息不再出现在上下文里，需要这里带过去。

### 2.3 一个具体的文件

下面是一个手写的示例（字段有删减），展示树结构在 JSONL 里的样子：

```json
{"type":"session","version":3,"id":"019a...","timestamp":"...","cwd":"/work/app"}
{"type":"message","id":"a1","parentId":null,"message":{"role":"user","content":"实现登录"}}
{"type":"message","id":"a2","parentId":"a1","message":{"role":"assistant","content":[...]}}
{"type":"message","id":"a3","parentId":"a2","message":{"role":"toolResult","content":[...]}}
{"type":"message","id":"a4","parentId":"a3","message":{"role":"assistant","content":[...]}}
{"type":"message","id":"b1","parentId":"a4","message":{"role":"user","content":"改用 JWT"}}
{"type":"message","id":"b2","parentId":"b1","message":{"role":"assistant","content":[...]}}
{"type":"branch_summary","id":"c1","parentId":"a4","fromId":"b2","summary":"..."}
{"type":"message","id":"c2","parentId":"c1","message":{"role":"user","content":"改用 session cookie"}}
```

文件是按时间顺序的一条直线，但 `parentId` 让它成为一棵树：

```text
a1 user "实现登录"
└─ a2 assistant
   └─ a3 toolResult
      └─ a4 assistant
         ├─ b1 user "改用 JWT"          旧分支
         │  └─ b2 assistant
         └─ c1 branch_summary            新分支，摘要了 b1-b2
            └─ c2 user "改用 session cookie"   当前叶子
```

当前叶子是 `c2`，所以发给模型的上下文是 `a1 → a2 → a3 → a4 → c1 → c2`，b 分支不在其中，但它的要点通过 `c1` 的摘要带了过来。下面几节逐步说明这些是怎么发生的。

### 3.2 appendMessage 与 _appendEntry

所有 `appendXxx` 方法都是同一个模式：构造 entry，`parentId` 取当前 `leafId`，交给 `_appendEntry`。

```ts title="packages/coding-agent/src/core/session-manager.ts:1191-1224"
	private _appendEntry(entry: SessionEntry): void {
		const previousLeafId = this.leafId;
		this.fileEntries.push(entry);
		this.byId.set(entry.id, entry);
		this.leafId = entry.id;
		try {
			this._persist(entry);
		} catch (error) {
			// Keep memory in line with the file: an entry that was not written must not become the
			// parent of later entries, or the file would hold entries pointing to a missing parent.
			this.fileEntries.pop();
			this.byId.delete(entry.id);
			this.leafId = previousLeafId;
			throw error;
		}
	}

	/** Append a message as child of current leaf, then advance leaf. Returns entry id.
	 * Does not allow writing CompactionSummaryMessage and BranchSummaryMessage directly.
	 * Reason: we want these to be top-level entries in the session, not message session entries,
	 * so it is easier to find them.
	 * These need to be appended via appendCompaction() and appendBranchSummary() methods.
	 */
	appendMessage(message: Message | CustomMessage | BashExecutionMessage): string {
		const entry: SessionMessageEntry = {
			type: "message",
			id: generateId(this.byId),
			parentId: this.leafId,
			timestamp: new Date().toISOString(),
			message,
		};
		this._appendEntry(entry);
		return entry.id;
	}
```

`_appendEntry` 先更新内存再写盘，写盘失败就回滚内存。注释说明了原因：如果内存里留着一条没写进文件的 entry，后面的 entry 会把它当 parent，文件里就出现指向不存在节点的 `parentId`，树就断了。

摘要类消息（`compactionSummary`、`branchSummary`）不能通过 `appendMessage` 写入，必须用专门的 `appendCompaction`、`branchWithSummary`，让它们成为独立的 entry 类型，便于查找。

### 3.3 延迟创建文件

```ts title="packages/coding-agent/src/core/session-manager.ts:1160-1189"

	 * A new session file is created only once the session contains a user or assistant message.
	 * Setup entries alone (model, thinking level, system prompt) stay in memory so opening and
	 * closing pi without chatting leaves no file behind. Starting at the user message (not the
	 * first assistant reply) keeps the prompt on disk if the first turn never completes (#10000).
	 */

		return this.fileEntries.some(
			(e) => e.type === "message" && (e.message.role === "user" || e.message.role === "assistant"),
		);
	}

	_persist(entry: SessionEntry): void {
		if (!this.persist || !this.sessionFile) return;

		if (!this.flushed) {
			if (!this._hasConversation()) return;
			const fd = openSync(this.sessionFile, "wx");
			try {
				for (const e of this.fileEntries) {
					writeFileSync(fd, `${JSON.stringify(e)}\n`);
				}
			} finally {
				closeSync(fd);
			}
			this.flushed = true;
		} else {
			appendFileSync(this.sessionFile, `${JSON.stringify(entry)}\n`);
		}
	}
```

启动 pi 时会先写入模型、thinking 级别、系统提示等设置类 entry。如果用户什么都没说就退出，不应该留下一个空会话文件。所以在第一条 user 或 assistant 消息出现之前，entry 只留在内存里；出现之后，用 `"wx"`（文件已存在则失败）一次性写出所有已有 entry，此后每条 entry 都是 `appendFileSync` 追加一行。

## 4. 上下文是树的投影

### 4.1 第一步：从叶子走回根

```ts title="packages/coding-agent/src/core/session-manager.ts:390-416"
function buildSessionPath(
	entries: SessionEntry[],
	leafId?: string | null,
	byId?: Map<string, SessionEntry>,
): SessionEntry[] {
	const index = buildEntryIndex(entries, byId);
	let leaf: SessionEntry | undefined;
	if (leafId === null) {
		return [];
	}
	if (leafId) {
		leaf = index.get(leafId);
	}
	leaf ??= entries[entries.length - 1];
	if (!leaf) {
		return [];
	}

	const path: SessionEntry[] = [];
	let current: SessionEntry | undefined = leaf;
	while (current) {
		path.push(current);
		current = current.parentId ? index.get(current.parentId) : undefined;
	}
	path.reverse();
	return path;
}
```

从叶子开始沿 `parentId` 往上走，直到根（`parentId` 为 `null`），再反转成从根到叶子的顺序。`leafId === null` 表示叶子在“所有 entry 之前”（重新编辑第一条消息时会出现），路径为空。`SessionManager.getBranch()`（[session-manager.ts:1479-1489](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/session-manager.ts#L1479-L1489)）是同一个算法的方法版本。

走一遍第 2.3 节的例子：叶子 `c2`，`c2.parentId = c1`，`c1.parentId = a4`，`a4 → a3 → a2 → a1`，`a1.parentId = null` 停止。反转后得到 `[a1, a2, a3, a4, c1, c2]`。`b1`、`b2` 不在任何一步的 parent 链上，自然被排除。

### 4.2 第二步：处理 compaction

路径上可能有 compaction entry。`buildContextEntries` 把“最新一次 compaction 之前、`firstKeptEntryId` 之前”的 entry 去掉：

```ts title="packages/coding-agent/src/core/session-manager.ts:468-512"
/**
 * Build the active, compaction-aware session entry list.
 *
 * This follows the current leaf path. If the path contains compaction entries,
 * the latest compaction is represented by the compaction entry itself, followed
 * by the kept entries starting at firstKeptEntryId and all entries after the
 * compaction entry. Older summarized entries are omitted.
 */
export function buildContextEntries(
	entries: SessionEntry[],
	leafId?: string | null,
	byId?: Map<string, SessionEntry>,
): SessionEntry[] {
	const path = buildSessionPath(entries, leafId, byId);
	let compaction: CompactionEntry | null = null;

	for (const entry of path) {
		if (entry.type === "compaction") {
			compaction = entry;
		}
	}

	if (!compaction) {
		return path;
	}

	const compactionIdx = path.findIndex((entry) => entry.id === compaction.id);
	if (compactionIdx < 0) {
		return path;
	}

	const contextEntries: SessionEntry[] = [compaction];
	let foundFirstKept = false;
	for (let i = 0; i < compactionIdx; i++) {
		const entry = path[i];
		if (entry.id === compaction.firstKeptEntryId) {
			foundFirstKept = true;
		}
		if (foundFirstKept && !(entry.type === "message" && entry.message.role === "system")) {
			contextEntries.push(entry);
		}
	}
	contextEntries.push(...path.slice(compactionIdx + 1));
	return contextEntries;
}
```

结果的顺序是：

1. compaction entry 本身（之后会变成摘要消息）；
2. 路径上从 `firstKeptEntryId` 到 compaction 之前的 entry（被保留的近期消息），跳过其中的 system 消息，因为 compaction entry 自己带了 `systemMessage`；
3. compaction 之后的所有 entry。

只看最新一次 compaction。更早的 compaction 已经被新的摘要吸收（新摘要是在旧摘要基础上更新的，见第 6.4 节），不需要再出现。

注意 compaction entry 在**文件里**的位置是在被保留消息的后面（它是压缩时追加的），但在**上下文里**被挪到最前面。这就是“投影”的意思：文件保存发生了什么，上下文按需要重新排列。

### 4.3 第三步：每条 entry 变成消息

```ts title="packages/coding-agent/src/core/session-manager.ts:435-466"

	}
	if (entry.type === "branch_summary" && entry.summary) {

	}

	}
	return [];
```

### 4.4 合起来：buildSessionProjection 与 buildSessionContext

```ts title="packages/coding-agent/src/core/session-manager.ts:542-583"
/** Build provenance-preserving, compaction-aware model context. */
export function buildSessionProjection(
	entries: SessionEntry[],
	leafId?: string | null,
	byId?: Map<string, SessionEntry>,
): SessionProjection {
	const path = buildSessionPath(entries, leafId, byId);
	const { thinkingLevel, model } = getSessionContextSettings(path);
	const contextEntries = buildContextEntries(entries, leafId, byId);
	const edits = new Map<string, ContextEditEntry>();
	for (const entry of contextEntries) {
		if (entry.type === "context_edit") edits.set(entry.targetId, entry);
	}
	const projectedEntries = contextEntries.map(
		(sourceEntry, index): ProjectedSessionEntry => ({
			sourceEntry,
			// buildContextEntries() may retain an older compaction entry because its
			// raw ID lies inside the newest retained range. Only the newest compaction
			// at index zero contributes a checkpoint and summary.
			messages:
				sourceEntry.type === "compaction" && index > 0
					? []
					: projectContextEntry(sourceEntry, edits.get(sourceEntry.id)),
		}),
	);
	return {
		entries: projectedEntries,
		messages: projectedEntries.flatMap((entry) => entry.messages),
		thinkingLevel,
		model,
	};
}

/** Build the finalized model context from the canonical session projection. */
export function buildSessionContext(
	entries: SessionEntry[],
	leafId?: string | null,
	byId?: Map<string, SessionEntry>,
): SessionContext {
	const { messages, thinkingLevel, model } = buildSessionProjection(entries, leafId, byId);
	return { messages, thinkingLevel, model };
}
```

完整的投影流程：

```text
buildSessionPath           叶子 → 根，反转            [a1 ... c2]
getSessionContextSettings  沿路径找最后的模型和思考级别
buildContextEntries        按最新 compaction 裁剪
收集 context_edit          targetId → 最新一条 edit
projectContextEntry        每条 entry → 消息，应用 edit
flatMap                    得到 AgentMessage[]
```

`ProjectedSessionEntry` 保留了“每条消息来自哪条 entry”（`sourceEntry`），所以叫“保留出处的投影”。compaction 需要这个信息来决定切点落在哪条 entry 上。`buildSessionContext` 只是丢掉出处，返回纯消息。

模型和思考级别也是从路径上算出来的：

```ts title="packages/coding-agent/src/core/session-manager.ts:418-433"

		if (entry.type === "thinking_level_change") {

		} else if (entry.type === "model_change") {

		} else if (entry.type === "message" && entry.message.role === "assistant") {

```

这里用的是完整路径而不是 compaction 裁剪后的列表，所以压缩前切换的模型仍然有效。不同分支可以用不同的模型：在 A 分支切到另一个模型，跳回 B 分支时投影出来的是 B 分支上最后使用的模型。

## 5. 分支：在旧节点继续对话

### 5.1 移动叶子指针

```ts title="packages/coding-agent/src/core/session-manager.ts:1583-1635"
	/**
	 * Start a new branch from an earlier entry.
	 * Moves the leaf pointer to the specified entry. The next appendXXX() call
	 * will create a child of that entry, forming a new branch. Existing entries
	 * are not modified or deleted.
	 */
	branch(branchFromId: string): void {
		if (!this.byId.has(branchFromId)) {
			throw new Error(`Entry ${branchFromId} not found`);
		}
		this.leafId = branchFromId;
	}

	/**
	 * Reset the leaf pointer to null (before any entries).
	 * The next appendXXX() call will create a new root entry (parentId = null).
	 * Use this when navigating to re-edit the first user message.
	 */
	resetLeaf(): void {
		this.leafId = null;
	}

	/**
	 * Start a new branch with a summary of the abandoned path.
	 * Same as branch(), but also appends a branch_summary entry that captures
	 * context from the abandoned conversation path.
	 */
	branchWithSummary(
		branchFromId: string | null,
		summary: string,
		details?: unknown,
		fromHook?: boolean,
		usage?: Usage,
	): string {
		if (branchFromId !== null && !this.byId.has(branchFromId)) {
			throw new Error(`Entry ${branchFromId} not found`);
		}
		const fromId = this.leafId ?? "root";
		this.leafId = branchFromId;
		const entry: BranchSummaryEntry = {
			type: "branch_summary",
			id: generateId(this.byId),
			parentId: branchFromId,
			timestamp: new Date().toISOString(),
			fromId,
			summary,
			details,
			usage,
			fromHook,
		};
		this._appendEntry(entry);
		return entry.id;
	}
```

`branch()` 只做一件事：把 `leafId` 设成目标 id。它不写文件，不删除任何东西。下一次 `appendMessage` 时新 entry 的 `parentId` 就是目标 id，目标节点从此有两个孩子，树就分叉了。

`resetLeaf()` 把叶子设为 `null`，下一条 entry 成为新的根。一个文件因此可以有多个根，`getTree()` 会把它们都返回。

`branchWithSummary()` 在移动叶子的同时追加一条 `branch_summary`，`fromId` 记录离开时的叶子位置。注意 `parentId` 是新位置而不是旧叶子，摘要挂在新分支上，这样它才会出现在新分支的投影里。

### 5.2 跳到不同类型节点的规则

用户在 `/tree` 里选中一个节点时，AgentSession 的 `navigateTree` 决定新叶子放在哪：

区分两种目标：

- **选中 user 消息**：意思是“我想重新问这个问题”。叶子放到它的**父节点**，原问题文本放回编辑器，用户可以修改后重新发送。新消息会成为原问题的兄弟节点。第 2.3 节的例子里，选中 `b1` 后叶子移到 `a4`，编辑器里出现“改用 JWT”，用户改成“改用 session cookie”发送，得到 `c2`。

最后调用 `_refreshFinalizedContext()` 重新投影，agent 的消息数组立刻变成新分支的内容。

## 6. Compaction：上下文压缩

### 6.1 什么时候触发


```ts title="packages/coding-agent/src/core/compaction/compaction.ts:264-270"
/**
 * Check if compaction should trigger based on context usage.
 */
export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
	if (!settings.enabled) return false;
	return contextTokens > contextWindow - settings.reserveTokens;
}
```

阈值是“窗口大小减去预留量”。以 200k 窗口为例：`200000 − 16384 = 183616`，上下文超过 183616 个 token 就压缩。预留 16384 是给下一次回复和工具结果留的空间：如果等到真正溢出才压缩，下一次请求就会失败。

两个参数的含义：

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `reserveTokens` | 16384 | 触发阈值 = 窗口 − 它 |
| `keepRecentTokens` | 20000 | 压缩后原样保留的近期消息大约有多少 token |

两者都可以在设置里配置，并且支持按模型覆盖（`compaction.modelOverrides["provider/id"]`，见 [settings-manager.ts:833-880](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/settings-manager.ts#L833-L880)）。

### 6.2 token 数从哪里来

最准确的数据是 provider 返回的 `usage`：上一次 assistant 回复的 `input + output + cacheRead + cacheWrite` 就是当时整个上下文的大小。之后新增的消息（工具结果、用户输入）还没有 usage，只能估算：

```ts title="packages/coding-agent/src/core/compaction/compaction.ts:192-224"
/**
 * Estimate context tokens from messages, using the last assistant usage when available.
 * If there are messages after the last usage, estimate their tokens with estimateTokens.
 */
export function estimateContextTokens(messages: AgentMessage[]): ContextUsageEstimate {
	const usageInfo = getLastAssistantUsageInfo(messages);

	if (!usageInfo) {
		let estimated = 0;
		for (const message of messages) {
			estimated += estimateTokens(message);
		}
		return {
			tokens: estimated,
			usageTokens: 0,
			trailingTokens: estimated,
			lastUsageIndex: null,
		};
	}

	const usageTokens = calculateContextTokens(usageInfo.usage);
	let trailingTokens = 0;
	for (let i = usageInfo.index + 1; i < messages.length; i++) {
		trailingTokens += estimateTokens(messages[i]);
	}

	return {
		tokens: usageTokens + trailingTokens,
		usageTokens,
		trailingTokens,
		lastUsageIndex: usageInfo.index,
	};
}
```

估算方法是“字符数除以 4”：

```ts title="packages/coding-agent/src/core/compaction/compaction.ts:294-330"
/**
 * Estimate token count for a message using chars/4 heuristic.
 * This is conservative (overestimates tokens).
 */
export function estimateTokens(message: AgentMessage): number {
	let chars = 0;

	switch (message.role) {
		// ...
		case "user": {
			chars = estimateTextAndImageContentChars(
				(message as { content: string | Array<{ type: string; text?: string }> }).content,
			);
			return Math.ceil(chars / 4);
		}
		case "assistant": {
			const assistant = message as AssistantMessage;
			for (const block of assistant.content) {
				if (block.type === "text") {
					chars += block.text.length;
				} else if (block.type === "thinking") {
					chars += block.thinking.length;
				} else if (block.type === "toolCall") {
					chars += block.name.length + JSON.stringify(block.arguments).length;
				}
			}
			return Math.ceil(chars / 4);
		}
```

英文大约 4 个字符一个 token，这个估算偏保守（倾向于多估），宁可早一点压缩。图片按固定 4800 字符计（`ESTIMATED_IMAGE_CHARS`）。

### 6.3 三种自动触发

`_checkCompaction` 在 agent 一次运行结束后（`_handlePostAgentRun`，[agent-session.ts:2008](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/agent-session.ts#L2008)）和新一次运行开始前（`_prepareRun`，[agent-session.ts:1931](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/agent-session.ts#L1931)）被调用，区分三种情况：

| 情况 | 判断条件 | 压缩后 |

| 溢出 | provider 返回上下文溢出错误 | 自动重试刚才的请求（最多一次） |

```ts title="packages/coding-agent/src/core/compaction/compaction.ts:446-501"
export function findCutPoint(
	entries: SessionEntry[],
	startIndex: number,
	endIndex: number,
	keepRecentTokens: number,
): CutPointResult {
	const cutPoints = findValidCutPoints(entries, startIndex, endIndex);

	if (cutPoints.length === 0) {
		return { firstKeptEntryIndex: startIndex, turnStartIndex: -1, isSplitTurn: false };
	}

	// Walk backwards from newest, accumulating estimated message sizes
	let accumulatedTokens = 0;
	let cutIndex = cutPoints[0]; // Default: keep from first message (not header)

	for (let i = endIndex - 1; i >= startIndex; i--) {
		const entry = entries[i];
		const messageTokens = sessionEntryToContextMessages(entry).reduce(
			(sum, message) => sum + estimateTokens(message),
			0,
		);
		if (messageTokens === 0) continue;
		accumulatedTokens += messageTokens;

		// Check if we've exceeded the budget
		if (accumulatedTokens >= keepRecentTokens) {
			// Prefer the closest valid cut point at or after this entry. If trailing
			// tool results exceed the budget by themselves, keep their preceding
			// assistant tool call instead of falling back to the first message.
			cutIndex = cutPoints.find((candidate) => candidate >= i) ?? cutPoints[cutPoints.length - 1];
			break;
		}
	}

	// Scan backwards from cutIndex to include adjacent metadata entries that do not affect context.
	while (cutIndex > startIndex) {
		const prevEntry = entries[cutIndex - 1];
		// Stop at compaction boundaries or context-visible entries.
		if (prevEntry.type === "compaction" || sessionEntryToContextMessages(prevEntry).length > 0) {
			break;
		}
		cutIndex--;
	}

	// Determine if this is a split turn
	const cutEntry = entries[cutIndex];
	const startsTurn = isTurnStartEntry(cutEntry);
	const turnStartIndex = startsTurn ? -1 : findTurnStartIndex(entries, cutIndex, startIndex);

	return {
		firstKeptEntryIndex: cutIndex,
		turnStartIndex,
		isSplitTurn: !startsTurn && turnStartIndex !== -1,
	};
}
```

逐步走一个例子，`keepRecentTokens = 20000`：

```text
idx  entry                 估算 token   从后累加
 0   user      "需求"         200
 1   assistant (toolCall)     300
 2   toolResult             30000      46900  超过 20000，停
 3   assistant               800       16900
 4   user      "继续"         100       16100
 5   assistant (toolCall)     400       16000
 6   toolResult             15000      15600
 7   assistant               600         600
```

从 7 往回加：7 → 600，6 → 15600，5 → 16000，4 → 16100，3 → 16900，2 → 46900，超过 20000，停在 `i = 2`。合法切点是 `[0, 1, 3, 4, 5, 7]`（2、6 是 toolResult），找 `>= 2` 的第一个，得到 `cutIndex = 3`。

然后向前扩展：如果 3 前面紧挨着模型切换、标签这类不产生消息的 entry，把它们也纳入保留范围，免得它们孤零零地被总结掉。

最后判断是否切开了 turn：entry 3 是 assistant，不是 turn 开头，往前找到 turn 开头 entry 0，所以 `isSplitTurn = true`、`turnStartIndex = 0`。

这里有两个“偏向保留”的选择：累加超额后选的是 `>= i` 的切点（往新的方向靠），所以实际保留的可能略少于预算；而当最后的 toolResult 自己就超过预算时，也会保留它前面的 toolCall，而不是退回到第一条消息。

实际的压缩流程用的是 `findProjectedCutPoint`（[compaction.ts:789-857](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/compaction/compaction.ts#L789-L857)），算法相同，但作用在 `ProjectedSessionEntry` 上，这样应用过 `context_edit` 之后的内容大小才是准的。它还多一条规则：如果切点之后只剩一次被省略的溢出重试尝试，切点再往后移一格。`findCutPoint` 作为公共 API 从包入口导出（[index.ts:41](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/index.ts#L41)）。

### 6.5 prepareCompaction：决定总结哪些消息

```ts title="packages/coding-agent/src/core/compaction/compaction.ts:859-923"
	pathEntries: SessionEntry[],
	settings: CompactionSettings,

	if (pathEntries.length > 0 && pathEntries[pathEntries.length - 1].type === "compaction") {

		(entry) => entry.sourceEntry.type === "compaction" && entry.messages.length > 0,
	);

	let boundaryStart = 0;

		previousSummary = (projectedEntries[prevCompactionIndex].sourceEntry as CompactionEntry).summary;
		// The canonical projection has already selected the previous compaction's retained tail.
		boundaryStart = prevCompactionIndex + 1;

	const boundaryEnd = projectedEntries.length;
	const tokensBefore = estimateProjectedContextTokens(projection, pathEntries).tokens;

	const firstKeptEntryId = firstKeptEntry.id;
	const historyEnd = cutPoint.isSplitTurn ? cutPoint.turnStartIndex : cutPoint.firstKeptEntryIndex;

	const messagesToSummarize = projectedEntries
		.slice(boundaryStart, historyEnd)
		.flatMap(getMessagesFromProjectedEntryForCompaction);
	const turnPrefixMessages = cutPoint.isSplitTurn
		? projectedEntries
				.slice(cutPoint.turnStartIndex, cutPoint.firstKeptEntryIndex)
				.flatMap(getMessagesFromProjectedEntryForCompaction)
		: [];

	if (messagesToSummarize.length === 0 && turnPrefixMessages.length === 0) return undefined;

	// Extract file operations from edited model-visible messages and the previous compaction.
	const fileOps = extractFileOperations(messagesToSummarize, sourceEntries, prevCompactionIndex);

	return {

		messagesToSummarize,

		previousSummary,

```

几个要点：

- **输入是当前分支的路径**（AgentSession 传入 `sessionManager.getBranch()`），先做一次投影。
- **增量压缩**。如果投影里已经有一次 compaction（它在投影的第 0 位），就把它的摘要作为 `previousSummary`，并且只在它之后的范围里找切点。新摘要是“旧摘要 + 新消息”合并出来的，所以旧的 compaction 不需要再进入上下文。
- **三段划分**。以前面的例子来说，`[boundaryStart, turnStartIndex)` 是 `messagesToSummarize`（历史），`[turnStartIndex, firstKeptEntryIndex)` 是 `turnPrefixMessages`（被切开的 turn 的前半段），`firstKeptEntryIndex` 之后原样保留。
- **路径末尾已经是 compaction 就不做**，避免连续压缩两次。
- 返回 `undefined` 表示没什么可压缩的，调用方直接放弃。

`CompactionPreparation` 这个中间结构会通过 `session_before_compact` 事件交给扩展，扩展可以取消压缩，或者自己生成摘要替换默认实现（[agent-session.ts:3184-3204](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/agent-session.ts#L3184-L3204)）。

```ts title="packages/coding-agent/src/core/compaction/utils.ts:120-163"
	for (const msg of messages) {
		if (msg.role === "user") {
			const content = contentText(msg.content, "");
```

## 7. 分支摘要：离开时带上要点

### 7.1 问题

5.2 节的导航只是移动叶子。离开的那条分支里可能已经做了很多探索：读过哪些文件、试过什么方案、为什么放弃。跳到新分支后这些全都不在上下文里了。分支摘要在离开时把这些要点总结一下，挂到新位置上。

### 7.2 收集要总结的 entry

```ts title="packages/coding-agent/src/core/compaction/branch-summarization.ts:110-148"
export function collectEntriesForBranchSummary(
	session: ReadonlySessionManager,
	oldLeafId: string | null,
	targetId: string,
): CollectEntriesResult {
	// If no old position, nothing to summarize
	if (!oldLeafId) {
		return { entries: [], commonAncestorId: null };
	}

	// Find common ancestor (deepest node that's on both paths)
	const oldPath = new Set(session.getBranch(oldLeafId).map((e) => e.id));
	const targetPath = session.getBranch(targetId);

	// targetPath is root-first, so iterate backwards to find deepest common ancestor
	let commonAncestorId: string | null = null;
	for (let i = targetPath.length - 1; i >= 0; i--) {
		if (oldPath.has(targetPath[i].id)) {
			commonAncestorId = targetPath[i].id;
			break;
		}
	}

	// Collect entries from old leaf back to common ancestor
	const entries: SessionEntry[] = [];
	let current: string | null = oldLeafId;

	while (current && current !== commonAncestorId) {
		const entry = session.getEntry(current);
		if (!entry) break;
		entries.push(entry);
		current = entry.parentId;
	}

	// Reverse to get chronological order
	entries.reverse();

	return { entries, commonAncestorId };
}
```

要总结的是“新位置看不到、旧位置看得到”的部分，也就是从旧叶子往上走到两条路径的最近公共祖先之间的 entry。公共祖先及以上的部分两边共享，不需要总结。

第 2.3 节的例子里，旧叶子是 `b2`，用户在树上选中 `b1`。`b2` 的路径是 `a1..a4, b1, b2`，`b1` 的路径是 `a1..a4, b1`，最深的公共节点就是 `b1` 本身，所以只收集 `b2`。`b1` 没有被收集，因为它是 user 消息：导航后新叶子落在它的父节点 `a4`，`b1` 的文本被放回编辑器，用户修改后重新发送，它的内容不会丢。

```ts title="packages/coding-agent/src/core/compaction/branch-summarization.ts:314-357"
		return { summary: "No content to summarize" };
	}

	// Transform to LLM-compatible messages, then serialize to text
	// Serialization prevents the model from treating it as a conversation to continue
	const llmMessages = convertToLlm(messages);
	const conversationText = serializeConversation(llmMessages);

	// Build prompt
	let instructions: string;
	if (replaceInstructions && customInstructions) {
		instructions = customInstructions;
	} else if (customInstructions) {
		instructions = `${BRANCH_SUMMARY_PROMPT}\n\nAdditional focus: ${customInstructions}`;
	} else {
		instructions = BRANCH_SUMMARY_PROMPT;
	}
	const promptText = `<conversation>\n${conversationText}\n</conversation>\n\n${instructions}`;
	// ...
	const context = normalizeContext({ systemPrompt: SUMMARIZATION_SYSTEM_PROMPT, messages: summarizationMessages });
	const requestOptions: SimpleStreamOptions = { apiKey, headers, env, signal };
	if (model.reasoning && thinkingLevel && thinkingLevel !== "off") {
		requestOptions.reasoning = thinkingLevel;
	}
	const response = await completeSummarization(model, context, requestOptions, streamFn, retry, callbacks);
```

调用路径和 compaction 共用：同样的序列化、同样的系统提示、同样的 `completeSummarization`。区别在提示词 `BRANCH_SUMMARY_PROMPT`（[branch-summarization.ts:260-287](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/compaction/branch-summarization.ts#L260-L287)）：它没有 Critical Context 一节，强调“这个分支想做什么、做到哪了”。结果前面加上一段说明（“用户在回到这里之前探索了另一个分支”），后面附上文件清单。用户还可以给出自定义指令，选择追加到默认提示后面或完全替换它。

`navigateTree` 把这些串起来（[agent-session.ts:4024-4216](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/agent-session.ts#L4024-L4216)）：

1. 正在流式输出或压缩时拒绝导航。
2. `collectEntriesForBranchSummary` 收集要总结的 entry。
3. 发出 `session_before_tree` 事件，扩展可以取消、提供自己的摘要、修改指令或标签。
4. 用户选择总结时调用 `generateBranchSummary`。
5. 按目标类型算出新叶子（5.2 节）。有摘要时 `branchWithSummary(newLeafId, ...)`，摘要成为新叶子；没有摘要时 `branch` 或 `resetLeaf`。
6. `_refreshFinalizedContext()` 重新投影，发出 `session_tree` 事件。

摘要只是让模型知道发生过什么。被离开的分支原封不动地留在树上，随时可以再跳回去。

## 8. 加载与版本迁移

最后看文件读进来的过程。`loadEntriesFromFile`（[session-manager.ts:627-670](https://github.com/earendil-works/pi/blob/44f6851b7f27ad5c18ccc94f6b4321650e757e3e/packages/coding-agent/src/core/session-manager.ts#L627-L670)）按 1MB 一块流式读取，逐行 `JSON.parse`，解析失败的行直接跳过。这是 JSONL 只追加格式的另一个好处：崩溃时最后一行写了一半，只损失这一行，前面的都能读。如果文件最后一行没有换行符（被截断的残行），加载后会补一个 `\n`，保证下一次追加从新的一行开始。第一行不是合法 header 的文件被视为不是 pi 会话。

旧格式在加载时就地迁移：

```ts title="packages/coding-agent/src/core/session-manager.ts:286-313"
/** Migrate v1 → v2: add id/parentId tree structure. Mutates in place. */
function migrateV1ToV2(entries: FileEntry[]): void {
	const ids = new Set<string>();
	let prevId: string | null = null;

	for (const entry of entries) {
		if (entry.type === "session") {
			entry.version = 2;
			continue;
		}

		entry.id = generateId(ids);
		entry.parentId = prevId;
		prevId = entry.id;

		// Convert firstKeptEntryIndex to firstKeptEntryId for compaction
		if (entry.type === "compaction") {
			const comp = entry as CompactionEntry & { firstKeptEntryIndex?: number };
			if (typeof comp.firstKeptEntryIndex === "number") {
				const targetEntry = entries[comp.firstKeptEntryIndex];
				if (targetEntry && targetEntry.type !== "session") {
					comp.firstKeptEntryId = targetEntry.id;
				}
				delete comp.firstKeptEntryIndex;
			}
		}
	}
}
```

v1 会话是一个线性列表，没有 `id/parentId`。迁移时给每条 entry 生成 id，`parentId` 指向前一条，线性列表就变成了一棵只有一根枝的树；compaction 原来用数组下标 `firstKeptEntryIndex` 记录切点，改成 id。这段迁移代码反映了设计的演进：先有线性会话和 compaction，后来为了支持分支才引入树。迁移后的文件通过 `_rewriteFile` 整体重写一次，这是 SessionManager 里少数会重写文件的地方。

## 小结

- 会话是 JSONL 文件，第一行是 header，之后每行一条 entry。entry 有 11 种类型，公共字段只有 `type`、`id`、`parentId`、`timestamp`。
- `parentId` 把 entry 连成树，`leafId` 指向当前位置。新 entry 总是挂在叶子下面，然后叶子前移。写盘失败时内存回滚，保证文件里不出现悬空的 `parentId`。
- 上下文是树的投影：`buildSessionPath` 从叶子走回根，`buildContextEntries` 按最新 compaction 裁剪，`sessionEntryToContextMessages` 把 entry 变成消息，`buildSessionProjection` 再应用 `context_edit`。模型和思考级别也沿路径计算。
- 在旧节点继续对话等于移动叶子指针。选中 user 消息时叶子落在它的父节点，原文本放回编辑器；选中其他消息时叶子落在它本身。
- `shouldCompact` 的阈值是“窗口 − reserveTokens（默认 16384）”。token 数优先用最近一次 usage，之后的消息按字符数除以 4 估算。
- `findCutPoint` 从最新往回累加到 `keepRecentTokens`（默认 20000），切点只落在非 toolResult 的消息上；切在 assistant 上时是 split turn，要额外总结 turn 前缀。
- 摘要把对话序列化成纯文本放进一条 user 消息，用固定格式的提示词，已有摘要时做增量更新，附带读过和改过的文件清单。
- compaction 和 branch summary 都只追加 entry，不修改不删除；被总结的内容仍在文件和树上，只是不再进入投影。
- 树导航时 `collectEntriesForBranchSummary` 找到最近公共祖先，总结旧叶子到祖先之间的部分，`branchWithSummary` 把摘要挂到新位置。
